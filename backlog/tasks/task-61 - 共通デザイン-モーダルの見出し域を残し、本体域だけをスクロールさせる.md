## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
snz-design TASK-20 の確認 (2026-09-27) で分かったこと。共通の `Dialog` (`components/Dialog.tsx`) が包む面 `ModalCard` (`styles/ui.tsx`) は、面そのものに `max-height: calc(100vh - 48px); overflow: auto` を持つ。どのモーダルも題名と閉じるボタンの行を面の中の先頭に置いているので、面の高さが画面を超えると、題名と閉じるボタンも中身と一緒に流れて見えなくなる。閉じるには上へ戻るか Escape を押すしかない。背後の画面は動かない。

snz-design doc-9 §6.6 (モーダル) は、面を見出し域・本体域・操作域に分け、「高さが画面を超えたら本体域だけがスクロールし、見出し域と操作域は残る」と求めている。snz-design は兄弟ディレクトリ `../snz-design` にある。

オーナー判断 (2026-09-27): `Dialog` を見出し域・本体域・操作域に分け、本体域だけをスクロールさせる。何を見出し域に置き、何を本体域に置き、操作域をどう持つかはアプリ側で決めてよい。今は全モーダルが部品を本体域に置く形で揃っている。閉じるボタンが流れるのは使い勝手が悪いので、見出し域を設ける。

`Dialog` を使う箇所 (2026-09-27 時点): 設定 (SettingsModal)、確認ダイアログ (ConfirmDialog)、プロジェクト作成 (CreateProjectDialog)、画像文書の追加 (ImageDocumentDialog)、チャットの題名・ドキュメント・編集レビュー (ChatPage)、発言のメモリ保存と結論 (MultiAgentChatPage)、ドキュメント詳細・題名・システムプロンプト・プロジェクトメモリ (ProjectDetailPage)。高さが出やすいのは設定・プロジェクトメモリ・ドキュメント・編集レビューのモーダル。

snz-design の適用記録 (doc-17) は、このタスクを §5 (未適用) の引き受け手として記録している。

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. styles/ui.tsx: ModalCard を flex の縦並び (overflow: hidden) にし、DialogHeader / DialogBody / DialogActions / DialogForm を足す。本体域だけが overflow-y: auto。本体域は焦点の枠の届く幅の余白と scroll-padding を持ち、枠がスクロールの箱で切れないようにする。見出し域・操作域は --snz-line-divider で区切る。
2. Dialog.tsx から見出し域・本体域・操作域の部品を出す (焦点の閉じ込め・Escape・返却の処理は触らない)。
3. 全モーダル (ConfirmDialog, CreateProjectDialog, ImageDocumentDialog, SettingsModal, ChatPage×3, MultiAgentChatPage×1, ProjectDetailPage×4) を3域に組み直す。単一フォームは実行を操作域へ、区画ごとに保存するもの・実行の無いものは操作域を持たない。
4. pnpm check:client / build:client。Vite dev server + Playwright (scratchpad、/api は route 固定) で、低い高さ・360px 幅での見出し域と操作域の保持、横スクロール無し、焦点の枠の切れ、Tab 閉じ込め・Escape・返却・破棄前確認、4配色の区切り線の比を測る。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- 組み方: `ModalCard` を縦並びの flex (`overflow: hidden`) にし、`Dialog.tsx` から `DialogHeader` (題名と、閉じるなどのボタン) / `DialogBody` (`overflow-y: auto`。スクロールするのはここだけ) / `DialogActions` (右寄せの操作域と、その上の失敗の告知) / `DialogForm` (本体域と操作域を1つのフォームで包む) を出した。見出し域の下と操作域の上の区切り線は `lineMedium` (= `--snz-line-divider`、doc-9 §6.6 のトークン用途)。焦点の閉じ込め・Escape・焦点の返却の処理 (`Dialog` 本体) は変えていない。
- モーダルごとの配置 (AC#2):
  - 確認ダイアログ: 見出し域=題名 (閉じるボタンは元から無い。取り消しが操作域にある) / 本体域=文面 / 操作域=取り消し・実行
  - プロジェクト作成: 見出し域=題名・閉じる / 本体域=題名・システムプロンプト / 操作域=作成
  - 画像文書の追加: 見出し域=題名・閉じる / 本体域=ドロップゾーン・プレビュー・各欄・説明の生成と生成の失敗 / 操作域=追加
  - チャットの題名: 見出し域=題名・閉じる / 本体域=題名・一時チャット・注記 / 操作域=設定を保存
  - プロジェクトの題名: 見出し域=題名・閉じる / 本体域=題名 / 操作域=名前を保存
  - システムプロンプト: 見出し域=題名・閉じる / 本体域=入力欄 / 操作域=保存
  - 多人数会話のメモリ保存・結論: 見出し域=題名・由来 (発言者 / 発言数) / 本体域=種別・内容・ロック・注記 / 操作域=キャンセル・保存
  - 設定: 見出し域=題名・閉じる / 本体域=全区画 / 操作域なし。外観は選んだ時点で保存し、接続の区画は区画の末尾の保存で保存する。区画ごとに保存するので、1つの操作域に置くとどれを保存するのかが読めなくなる
  - ドキュメント詳細: 見出し域=題名・種類とカテゴリの行・閉じる / 本体域=残り全部 / 操作域なし。カテゴリの保存・全チャットで共有・画像文書の編集 (編集中は編集器の保存と取り消し) がそれぞれ別の対象を保存する
  - プロジェクトメモリ: 見出し域=題名・整理・閉じる / 本体域=整理案 (適用)・メモリの追加フォーム (保存)・一覧 (行ごとの共有・ロック・削除) / 操作域なし。操作が区画ごとに別の対象に効く
  - ドキュメント追加 (チャット): 見出し域=題名・閉じる / 本体域=ドロップゾーンと失敗 / 操作域なし。ファイルを選ぶかドロップした時点でアップロードが始まり、押す実行が残らない
  - 編集レビュー: 見出し域=題名・閉じる / 本体域=レビューと参照 / 操作域なし。読むだけで、コピーのボタンはコピーする本文の側に置く
- 実行を操作域へ移すかは、PR 前にオーナーが確認し、上の7つを移す形に決めた (2026-09-28)。
- 実行の失敗の告知は、本体域の先頭ではなく操作域の中、実行のボタンの上に置いた (doc-9 §6.6 の擬似コードは「本体域の先頭」)。本体域をスクロールした後で実行を押すと、本体域の先頭の告知は見えない位置に出る。操作域は常に見えている。TASK-57 が揃えた「告知 → ボタン」の並びもこれで保たれる。
- 題名・システムプロンプト・チャットの題名のモーダルは、フォームを包んでいた `Card` を外した。ボタンが操作域へ移ると Card の中に欄だけが残る。同じ形のプロジェクト作成のモーダルは元から Card を持っていない。
- 焦点の枠 (AC#3): 本体域は枠の届く幅 (`FOCUS_RING_REACH`、3px) より大きい余白 (上 16px・左右 20px・下 20px) を持ち、`scroll-padding-block` に同じ幅を置いた。見出し域と操作域は本体域に重ならない (flex の兄弟) ので、焦点を受けた部品を覆わない。
- 測定環境 (snz-design doc-5 §5.3): アプリ snz_studio、ブランチ `task-61-modal-scroll-regions` (main `2600b2a` 起点の作業ツリー)。共通仕様 snz-design tokens 0.1.1 (写しは変更なし)。OS macOS 26.6.2。描画エンジン Playwright 1.62.1 の Chromium 151.0.7922.34 / WebKit 26.5 (headless、WKWebView ではない)。倍率 1、ウィンドウ 1280×800・1280×420・360×640・360×420。入力は Playwright の合成事象。WebKit は Option+Tab で巡った (Tab だけではボタンに届かない既定のため。実アプリは Wails の TabFocusesLinks で有効)。配色は標準 Light / 標準 Dark / Solarized Light / Solarized Dark。表示言語 ja。測定日 2026-09-28。画面は Vite 開発サーバー、/api/* は route の固定 JSON (リポジトリには足していない)。
- 結果 (12 モーダル × 4 寸法 × 2 エンジン = 96 通り、すべて合格):
  - AC#1: 面が画面に収まり、見出し域 (と操作域) が画面内にある。本体域があふれる場合は、本体域を末尾までスクロールしても見出し域・操作域の位置が動かない。本体域のほかにスクロールする箱は無い (テキストエリアを除く)。1280×420 では 7 モーダル、360×420 では 11 モーダルで本体域がスクロールした。
  - AC#3: 高さ 420 の2寸法で、各モーダルの操作部品を最後まで Tab で巡った (1 モーダルあたり 2〜33 か所)。焦点を受けた部品が本体域の見える範囲から完全に外れることは無かった。部品が本体域に収まっている辺で、枠 (outline の幅 + offset) が本体域に切られることも無かった。本体域より背の高いテキストエリアは、はみ出た辺が切れる。スクロールするページで起きるのと同じで、枠が切れているのではない。WebKit は焦点が移ってから非同期に本体域をスクロールするので、50ms 待ってから測った。
  - AC#4: 1280×800 と 360×420 で、両エンジンとも次を確かめた。プロジェクト作成で書きかけのまま Escape を押すと破棄前確認が出る。確認では「編集を続ける」に焦点が置かれ、Shift+Tab / Tab が確認の中で回る。Escape は確認だけを閉じ、入力は残る。作成の失敗の告知が操作域に出て画面内にある。破棄すると両方が閉じ、焦点が「新しいプロジェクト」へ戻る。題名のモーダルは書きかけが無ければ Escape で確認なしに閉じ、焦点がトリガーへ戻る。多人数会話のメモリ保存は、キャンセルで閉じると焦点が「メモリに保存」へ戻る (returnFocusTo)。96 通りのどれでも、ページ・面・本体域に横スクロールは出なかった。
  - AC#5 の比 (Chromium で計算した値。標準 Light / 標準 Dark / Solarized Light / Solarized Dark): 区切り線 (見出し域の下・操作域の上) 対 面 1.39 / 1.31 / 1.33 / 1.19。doc-5 §3.2 の「装飾の区切り線」にあたり、下限は無い。外周の罫と同じ色。見出しの語 対 面 14.42 / 11.44 / 12.05 / 10.61、見出し域の補足 (Subtle) 対 面 6.55 / 6.72 / 5.73 / 4.86。色の値は変えておらず、面 (`surfaceCard`) の上に置く場所が変わっただけ。3つの域は背景を持たない (透明)。
- 未確認: 実窓 (WKWebView) での目視はオーナーの確認待ち。AC#5 はそれまで未チェックのままにする。画像文書の追加で実際の画像を選んだ状態 (プレビューが出る) と、ドキュメント詳細で画像文書を編集している状態は、本体域が長くなる場合として実窓で見てほしい。
- `pnpm check:client`・`pnpm build:client` が通った (build は既存の chunk サイズ警告のみ)。
- snz-design doc-17 の §2・§3 の行 (全モーダルの意図的な例外) を直す作業は snz-design 側に残した。

- レビュー (#63 第1回) 対応: 見出し域は固定でスクロールしないので、長い題名 (ドキュメントの題名に長さの上限は無い) で見出し域が面を超え、閉じるボタンと本体域が面の外に切れた (360×420、題名 1,000 字で再現)。見出しを3行、その下の行 (多人数会話の発言者名なども上限が無い) を2行で切るようにした。全文は DOM に残るので支援技術は読み上げる。ドキュメントの題名は見出しの title 属性にも入れた。長い入力 (題名 W×1,000、参加者名 600 字) のドキュメント詳細と多人数会話のメモリ保存で 4 寸法 × 2 エンジンが合格した。見出し域のボタンが面の中にあること、本体域が 40px 以上残ることも合わせて確かめた。修正を戻すと 360×420 などの 3 通りが落ちることも確かめた。通常の入力の 96 通りも再び合格した。
