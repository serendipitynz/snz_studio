## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 背景

設計書 §4.9 の履歴の選び方を実装する。値 (参加者 1 人あたりの予算・R・換算係数・加点) は TASK-103 の測定で決めたものを使う。
ピン留め (TASK-105) と、選抜発言・切り詰めの参照表示 (TASK-106) は別タスクで、このタスクではピン留めの加点を入れない。

## やること

- 窓上限: 話者のモデルのロード時のコンテキスト長から system prompt・進行文・生成分を引いて文字数に換算する。取れないときは既定値。0 以下ならターンを始めず、長すぎる設定を返す (§4.9.2 手順 1)
- 履歴予算 = min (参加者 1 人あたりの予算 × 参加者数, 窓上限)。参加者数は現在の名簿の人数。予算は写像後の文字数 (表示名の前置き・【ダイス】【効果】行・省略行を含む) で数える (手順 2)
- 末尾の発言: 参加者 1 人あたりの予算は超えてよいが窓上限は超えない。超えるときは先頭と末尾を半分ずつ残して中略する (手順 3)
- 直近区間: 末尾から参加者の発言が参加者数 × R 件含まれるまで。予算を超えたら新しい側から収まるだけ入れ、手前に省略行を置き、選抜発言は入れない (手順 4)
- 発言スコア: 人間の介入・反響・今のターンとの関連・話者との関わり・会話の先頭 (§4.9.3)。同点は新しい発言を優先
- 選抜発言: スコア順に応答先とペアで、増える省略行の分も含めて予算に収まるものを足す。時系列に並べ、連続しない箇所に省略行 (独立した user メッセージ) を挟む (手順 5・6)
- `TurnHistoryLimit` を廃し、`GET /api/chats/{chatId}/turns/next` の `historyLimit` を R を返す欄に替える。観戦ビューの `(?)` の説明を直す
- §4.9.8 の既存記述 (設計書 §4.3・§4.4・§5・§6・§8.1、current-spec (en/ja)、multi-agent-presets.md) を実装に合わせて書き換える

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
§4.9.2・§4.9.3 の組み立てを internal/service/turnhistory.go に実装し、TurnHistoryLimit を廃した。値は TASK-103 で決めたもの（1 人 2,000 字、R = 2、換算係数 1.0、生成に残す分 2,048 トークン、既定のコンテキスト長 8,192 トークン）。

設計書に書いていなかった判断:

- プロンプトの組み立てを SSE の speaker 通知より前へ移した。長すぎる設定の拒否を 400 で返すには、ストリームを開く前に system prompt の長さが要るため。代償として、検索の分だけ speaker の通知が遅れる。
- 窓上限から進行文を常に引く。進行文を使うかどうかは、これから組み立てる履歴で決まるため。答えるべき発言があるターンでは進行文の分だけ窓が狭くなる。
- 省略行と中略の目印は、件数が最大のときの長さで予約する。実際の件数は選抜の後でしか分からないので、桁が減る分は余りになる。
- 窓上限が省略行より短いときは、末尾の発言だけを窓に切り詰めて送り、省略行は置かない（設計に無い極端な場合）。
- 最後の検査に通らないときはターンを失敗させる（errTurnHistoryOverWindow、500）。送っても接続先の exceed_context_size_error になるだけなので、黙って送らない。

観戦ビューの説明はピン留めに触れていない（§4.9.5 の文面のピン留めの部分は TASK-105 で足す）。multi-agent-presets.md の 4 名の上限は値を残し、理由だけを書き換えた。上限を残すかは未判断。

確認: go test ./...、go vet ./...、pnpm run check:client、pnpm run test:client（32 件）が通る。AC の #1〜#6・#8 は turnhistory_test.go。窓上限の不変条件は 1〜7,000 字の窓を 13 字刻みで確かめた。LoadedContextLength の読み取り先は、動いている LM Studio の /api/v1/models でも確かめた（gpt-oss-20b で 40960。同じ key が 2 項目並ぶ gemma も確認）。

確かめていないこと: 実モデルでの会話の通し実行と、アプリの画面での (?) の表示。新しい組み立ての崩れ方は TASK-103 の使い捨てスクリプトの結果しかなく、この実装そのものでは測っていない。

マイルストーンは付けていない。TASK-103・105・106 も付いておらず、タスク本文にも指定が無いため。
