## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 背景

TASK-107 の測定 (gpt-oss-20b、581 ターン) で、`LLM stream did not contain message content` によるターンの失敗が 2 回出た。

- 同梱 trpg-table の開幕の GM (役割リマインドの言語の行を除いた対照の条件。約 20 秒で失敗)
- 同梱 twenty-questions の 2 ターン目の出題者 (現行の条件。約 1.3 秒で失敗)

このエラーは、ストリームを整形した後の表示本文が空のときに `CreateChatCompletionStream` が返す。`RunTurn` はそのままターンを失敗させ、発言は保存されない。

原因は確かめていない。測定では生のストリームを保存しなかった。`buildTurnPrompt` のコメントには、gemma-4-e4b が推論だけを返して本文が空になった記録があるが、今回の 2 回が同じ現象かは分からない。所要時間も大きく違う。

## 変えるもの

本文が空で失敗したターンを、同じ話者で 1 回だけやり直す。本文がまだ何も出ていない失敗なので、発言の重複や順番のずれは起きない。設計書 §4.2 が禁じているのは別の参加者への切り替えと代替文の挿入で、同じ話者の再試行はそのどちらでもない。

空応答そのものを減らす修正ではなく、起きても会話が止まりにくくする修正である。

## 決めること

- 1 回目の推論は画面に流れているので、再試行のときに表示をどうするか (リセットするか、再試行したことを出すか)。
- 再試行するのは多人数会話のターンだけか。1 対 1 チャットも同じエラーを返すので、含めるかを決める。

## 対象外

- 推論の文がタグなしで本文に混ざる現象 (TASK-107 の測定で 581 ターン中 1 回)。目印が無く、文面からの推定は正しい発言を削る恐れがあるので、ここでは扱わない。

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. llmclient: 本文が空のエラーを sentinel (ErrEmptyCompletion) にし、finish_reason・生の本文と推論の文字数・completion_tokens を持つ型で返す (文面は従来どおり)。ログで原因を追えるようにする

3. TurnEngine.RunTurn: ErrEmptyCompletion のときだけ、同じ話者・同じ prompt で 1 回だけ再試行する。再試行の前に Restart を流し、ログを残す。2 回目も空なら従来どおり失敗し保存しない。1 対 1 チャットは対象外 (ユーザー判断)

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 判断（2026-11-07、ユーザー）
- 再試行の表示: 「消して一言出す」。`retry` SSE で 1 回目の推論と本文を消し、生成中の吹き出しに「本文が空の応答だったため、同じ話者でもう一度生成しています。」を出す。完了後は消える。
- 対象: 多人数会話のターンだけ。1 対 1 チャットは変えていない。
- 1 回に限る理由は「連続で空ならモデルが答えられない」ではなく、繰り返すと自動進行がそのターンで止まり続けるため、とした（測定では空は試行ごとにほぼ独立に起きるので、前者は根拠にならない）。

## テスト（AC #1・#2・#5）
- internal/service/turnretry_test.go: 空→答えで 2 回同じリクエストを送り、Restart が 1 回、2 回目の発言だけが同じ話者で保存される。空→空で ErrEmptyCompletion、3 回目は送らず何も保存しない。500・タイムアウト・不正 JSON は 1 回で失敗し再試行しない。
- 空応答のエラーは finish_reason・本文/推論の文字数・トークン数を持ち、ログに出す（文言は従来どおり）。
- go vet ./...、go test ./...、pnpm run check:client、pnpm run test:client が通る。

## 実機確認（AC #3）
- pnpm dev（DATA_DIR は一時ディレクトリ）を 192.168.0.219 の openai/gpt-oss-20b につなぎ、奇数回目の応答から本文を抜くプロキシを挟んで再試行を起こした。
- 1 回目の推論が流れたあと、推論が消えて一言が出て、2 回目の推論が最初から流れた。完了後は一言が消え、2 回目の本文と推論だけが 1 ターン目として保存された。

## 測定と原因（AC #4）
- 同梱プリセット twenty-questions 8 ターン × 40 回、trpg-table 5 ターン × 40 回を各モデルで実ターンエンジンに通し、生ストリームを記録した。
- gpt-oss-20b: twenty-questions 292 ターンで空の試行 36/321。29 ターンで再試行し 22 ターンが回復、7 ターンが 2 回目も空で失敗（空による失敗 9.9% → 2.4%）。出題者 25/165、回答者 11/156。trpg-table は 200 ターンで 0。
- gemma-4-e4b-it-qat: 520 ターンで推論だけの空応答は 0。途中で閉じたストリームが 2 回あり、どちらも再試行で回復。
- gpt-oss の空応答は finish_reason=stop、本文 delta 無し、completion−reasoning tokens は 10〜98（中央値 22、答えた試行は 24）。答えは書かれているが本文として返っていない。
- 再現: 空になったリクエストを非ストリームで 7/25、Responses API で 7/20 が空。/v1/completions に harmony 生プロンプトで 30 回送ると 6 回が答えを `commentary to=assistant <|constrain|>response`（または json）に書いていた。ツール呼び出しの形なので LM Studio が本文として返していないと見ている。推論の打ち切りではない。
- 推論の途中で finish_reason も [DONE] も無く閉じたストリームが gpt-oss で 3 回、gemma で 2 回。本文が無いので空として再試行される（4 ターン回復）。原因は未確認。

## 測っていないこと
- 途中で閉じたストリームの原因。測定は記録用プロキシ越しで、プロキシは上流の読み取りエラーも正常終了として渡すため、直接つないだときにアプリが読み取りエラー（再試行しない）として受けるかは確かめていない。
- 1 対 1 チャットでの空応答の頻度。

## 追記（2026-11-08）
- 推論の途中で閉じたストリーム（gpt-oss 3 回、gemma 2 回）は、測定中に別のマシンが同じ LM Studio を使っていたためと見られる（ユーザーの見立て。各ストリームの時刻は記録していないので突き合わせていない）。測定環境による現象で、gpt-oss の空応答とは別に扱う。設計書 §8.1 の TASK-112 の項にも追記した。
