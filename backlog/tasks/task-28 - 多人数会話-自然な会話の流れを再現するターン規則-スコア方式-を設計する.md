## Description

## 背景

ターン規則は現在 `round_robin` と `manual` で、TASK-21 が「進行役を 1 人おきに挟む」規則を足す。
いずれも順番が固定で、実際の会話にある「呼ばれた人が答える」「しばらく黙っていた人に話が回る」
「同じ人が続けて話さない」といった流れは出ない。この spike では、そうした自然な会話の流れを
決定的なロジックとして表現できるかを設計し、実装タスクを切るかを判断する。既存の 3 規則は置き換えず、
第 4 の規則として並置する前提で検討する。

## 出発点となる案 (スコア方式)

ターン開始時に参加者ごとの重みを計算し、最大の参加者が話す。重みは次の規則の係数の積と定義する。原案の「減った分を他の参加者に按分する」操作は
係数の積と等価ではなく (等重みの 3 人で A を ×0.2 して比例按分すると 1:7:7、積を正規化すると 1:5:5)、
按分は規則の適用順序にも依存する。順序に依存せず説明しやすい積の定義を採り、合計 1 の正規化は表示用にだけ行う:

- 現ターンの発言者 ×0.2 (同じ人が続けて話さない)
- 沈黙優遇: 参加者人数ターン以上発言していない参加者を相対的に上げる (原案では直近 n ターンに発言した
  非進行役を ×0.85。定常状態ではほぼ全員に当たるので「沈黙者を上げる」と書くほうが読みやすい)
- 指名: 直近の発言が次の話者を名指ししていれば、それ以外を ×0.5
- 名簿順の次の参加者以外を ×0.95 (何もなければ round_robin に近づける)
- 進行役 (任意): 沈黙優遇の対象外にする

原案の係数で積を取ると、指名も長い沈黙も無いあいだは、直近に発言した非進行役は最大 0.85、進行役は現ターン発言者で
ない限り 0.95 以上なので、進行役が 1 ターンおきに挟まる (TASK-21 に近い振る舞いが係数から出る)。ただし保証ではない:
指名があれば進行役も ×0.5 を受ける (名簿 GM, A, B, C で直前発言者 A が B を指名すると GM 0.475 < B 0.85)。
長く沈黙した参加者 (1.0) も進行役 (0.95) に勝つ。TASK-21 の確定的な交互進行の代替にはならないので、並置が前提。
また名簿 GM, A, B, C で直前発言者が A、名簿順の次 B が直近に発言済み、C が長く沈黙、のとき C と GM が
0.95 で並ぶ。同点規則が必要。

この案が唯一の候補ではない。自然な流れを別の形 (例: 規則の優先順位付きの決定木) で表現できるなら
そちらでもよく、比較して選ぶ。

## 制約 (設計書 §2 を保つ)

- 次の話者は名簿と保存済み発言だけから導出し、サーバー側に進行状態を持たない (再起動・複数ウィンドウで同じ答え)。
- 指名の検出結果は発言の保存時に確定して発言側に保存する (`nominated_participant_id` 相当)。後から本文を
  再解釈すると再起動前後で答えが変わり得る。
- 判定のための追加の LLM 呼び出しはしない (設計書 §8.1 が履歴要約を見送った理由と同じ: 小型モデルで 1 ターンの遅延が倍になる)。
- 人間の介入発言は名簿にいないので、「名簿順の次」は直近の参加者発言から取り、指名の検出は直近の発言 (人間含む)
  に対して行う。名指しの無い介入の後に誰が話すかは決めること 5 に含める: 直前の参加者発言を「現ターンの発言者」として
  ×0.2 を課すと、進行役が話した直後に人間が介入した場合に進行役が応じられない (GM 0.19 < 名簿順の次 0.85)。

## このタスクで決めること (実装はしない)

1. 規則の集合と係数、同点規則。3〜4 人 (進行役あり/なし) で数十ターンを回す簡単なシミュレーション
   (スクリプトでよい) で、同じ人の連続、全員に発言が回るまでのターン数、進行役の挟まり方を確認して決める。
   指名がある場合と、名指しの無い人間の介入の後の場合をシナリオに含める。
2. 指名の検出方式。候補: (a) 役割リマインダーで末尾に `[次: 表示名]` を書かせ、保存前に剥がして記録する
   構造化出力 (設計書 §4.3 のとおり小型モデルは書式を模倣しやすい。剥がし損ねの防御が要る)、
   (b) 直近発言の末尾文に他の参加者の表示名 (+「さん」「?」など) があれば指名とみなす名前照合
   (三人称の言及を誤検出する。(a) の空振り時のフォールバック向き)。推奨は (a) + (b) のフォールバック。
3. 次話者表示の出し方。フロントの `predictNextSpeaker` (`turnOrder.ts`) は round_robin を複製しているが、
   この方式は算術を二重に持つべきでないので、サーバーが次話者と重みの内訳を返す形を検討する。
4. 実装タスクを切るか。切る場合は TASK-21 の TRPG 卓プリセットを検証シナリオの 1 つにする。
5. 名指しの無い人間の介入発言の後の話者。候補: 人間の発言を「現ターンの発言者」とみなして参加者の誰にも ×0.2 を
   課さない (進行役が沈黙優遇の対象外である分だけ応じやすくなる)、または介入後は進行役を優先する明示規則。
   TASK-21 が設計時に決める「人間の介入発言を挟んだ後に誰が話すか」と揃える。

各案の利点・欠点と推奨を設計書 `docs/multi-agent-chat-design.md` に追記する (§8.2 の「進行役モデルによる
発言者指名」の項と整合させる)。

## 結論: スコア方式 (`weighted`) を採用 (ユーザー判断)

対案として、呼びかけ先を最優先する係数なしの順位規則 (`addressed_first`) も書いて測った。
**呼びかけ先が 1 人のあいだ、両者は同じことをしている** (追従率 17/17 対 22/22、他の観測量の差は
進行役の間隔 1〜3 対 1〜1 のみ)。差が出るのは 1 発言が 2 人以上を呼ぶ場合で、順位規則は一方を
捨てるしかなく、捨てられた側の待ちが 14 ターン・一巡ターン数 17 に伸びる。スコア方式は
呼びかけ先の全員が ×0.5 を免れるので、待ち 5 ターン・一巡 8 に収まる。
「A さんと B さん、どう思う？」は普通に起きる発言なので、これが決め手になった。

## 起票時の見込みと違っていた点

- **呼びかけの集中 ×0.5 は「重みへの影響」ではなく勝敗の決定として働く。** 呼びかけ先は最低
  0.85×0.95 = 0.8075、他の最大は 0.5 なので、他の 3 係数が何をしようと呼びかけ先が勝つ。
  呼びかけ先を上げる形に書き換えて上げ幅を下げると、境界は 1/(0.85×0.95) ≈ 1.238 にあり、
  ×1.3 で 17/17、×1.2 以下で 6/19 に落ちる。係数が離散値の固定集合なので比較が階段関数になり、
  連続的な影響力は持てない。よって ×0.5 より強める意味はない。
- **起票時に予想した「係数から進行役が 1 ターンおきに挟まる」は再現しない。** 実際は間隔 1〜3 の
  不規則で、`facilitator_alternating` の 1〜1 にも `round_robin` の 3〜3 にもならない中間。
  この違いを作っているのは直近発言の抑制 (×0.85) と進行役の免除だけで、どちらを外しても
  `round_robin` と完全一致する。
- **起票時に「沈黙優遇」が担うと書かれていた「しばらく黙っていた人に話が回る」性質は、実際には
  同点規則が担っていた。** 同点を名簿順で割ると一巡ターン数が 12 まで伸び、沈黙が長い側を採ると 7 に収まる。
- **呼びかけが無く進行役も居ない編成では、スコア方式は `round_robin` と 1 発言も違わない。**
  `weighted` を選ぶ意味があるのは、呼びかけが起きる編成か進行役が居る編成である。

## 語彙

起票時の「指名」は既に 2 つの対象 (`manual` の人間指名、§7 の進行役指名) に使われていたので、
発言本文が相手の表示名を挙げることには **呼びかけ** を与えた。保存先は単数の
`nominated_participant_id` ではなく、**参加者 id の集合**とした (複数呼びかけを表現できることが
`weighted` を採る理由そのものなので、単数に切り詰めない)。「沈黙優遇」は積の定義では係数を
掛けない側なので、実際に係数が掛かる **直近発言の抑制** と呼び替えた。
対応表を本文より先に確定してから書いている (CLAUDE.md の Semantic discipline)。表は 3 版まで改訂した
(連続発言率の定義訂正、呼びかけの単数→複数、採用案の入れ替え)。

## 決めること 3 (次話者と重みの内訳の提示)

`speaker` イベントをターンの SSE に足し、話者と重みの内訳を載せ、`turnOrder.ts` の複製を消す。
位置は `endpointAccepts` の直後に限られる (`handleRunTurnStream` は最初の delta まで SSE ライタを
開かず、それがターン前の失敗を HTTP ステータスで返すための作りである)。
**409 / 404 / 400 / 502 は残るが、生成そのものの失敗の HTTP 500 はストリーム内 `error` に変わる。**
同じ失敗が「delta が 1 つでも届いたか」で 500 とストリーム内 error に分かれる現在の挙動より揃うので
改善として受け入れ、TASK-33 の検証項目に固定した (この点は Codex レビューの [P2] 指摘で修正)。

## 決めること 5 (人間の介入の後)

人間の発言を「現ターンの発言者」とみなし、連続発言の抑制 ×0.2 を誰にも課さない。
×0.2 を課し続けると、人間が直前の話者を名指しで呼んでも 0.2×0.85×0.95 = 0.1615 にしかならず
他の最大 0.5 に負け、追従率 0/12 になる。現ターンの発言者とみなすと 0.8075 で 12/12。
「介入後は常に進行役」も同じ理由で 0/12 なので、TASK-21 の答えとはこの 1 点で揃わない。
名指しの無い介入に限れば両者の結果は近い (一巡 7 対 9、追従 18/20 対 19/20)。

## 追記 (2026-09-22、Codex レビュー第 2 巡の [P2] 4 件): 採用理由を訂正した

4 件すべて正当だった。うち 2 件は、いったん記録した根拠そのものを崩すものだったので訂正した。

- **シミュレータの「採用」行が仕様と違っていた**: 名指しの無い介入で進行役を強制する上書きを掛けており、
  §4.6.7 が書いている「重みで決める」形を測っていなかった。仕様どおりの行を足して測り直し、
  上書きは別行として残したうえで**採らない**と決めた (§4.6.7)。
- **複数呼びかけ待ちが未応答を取りこぼしていた**: 応答されなかった呼びかけを最大値から外していたため、
  誰も答えなかった transcript が「待ちが短い」と読めていた。未応答件数を併記する形に直した。
- **「順位規則は呼びかけ先の一方を捨てるしかない」は誤りだった**: 比較用に書いた実装が集合の先頭を
  採っていただけで、順位規則一般の限界ではない。呼びかけ先の集合から沈黙が長い側を採る順位規則を足して
  測ると、係数も同点規則も持たずに追従率 30/30・未応答 0・同点 0 を出す。`weighted` は待ちの最大値
  (5 対 7) と一巡ターン数 (8 対 10) で勝つが、28 件中 2 件を未応答で終え、同点規則も要る。
  **測定上は互角で、どちらも一方的に優れてはいない。**
- **呼びかけ係数の閾値の解釈が誤りだった**: 1.238 は「最悪の重みの組み合わせでも勝つ」十分条件の境界で、
  上下で切り替わるスイッチではない。境界を下回っても追従は段階的に落ちるだけで (×1.2 は呼びかけ 3 割・
  介入なしで 17/17、介入ありで 16/20、×1.1 で 12/20 と 6/19、係数なしで 5/19)、数値も scenario を
  取り違えていた。

**その結果、`weighted` を採る理由を書き換えた。** 測定上の優位ではなく、**呼びかけの強さを他の係数と
同じ土俵で調整できる表現力**にある (順位規則には「呼びかけが常に最優先」の一点しかなく、この調整幅が無い)。
採用そのものはユーザー判断として変わらず、既定は原案の係数 (呼びかけを必ず通す設定) とした。

また **どちらの規則も、応答されなかった呼びかけを次の 1 ターンより先へ持ち越さない**ことを明記した。
`weighted` の「呼びかけ先の全員が ×0.5 を免れる」は、その 1 ターンで誰が話すかを決めるだけで、
2 人目に順番を保証しない。持ち越しは §2 の「サーバー側に進行状態を持たない」と両立する導出の設計が
別途必要なので、TASK-34 の範囲外として明記した。
