## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 背景

TRPG では HP・所持品・現在位置・残り時間のような状態がターンごとに変わる。これは耐久性のある事実では
ないのでメモリに入れると汚れ (TASK-19 の趣旨に反する)、静的でもないのでドキュメントにも向かない。
現状の受け皿は場面設定 (`scene_prompt`) を人手で更新することだけで、履歴は直近 30 件で切られるため
古い状態変化は自然に消える。

## このタスクで決めること (実装はしない)

1. 状態の表現: 場面設定を「固定の設定」と「現在の状態」に分けるか、chat に別の自由文
   (状態シート) を 1 つ足すか、参加者ごとのシートにするか。
2. 更新の主体: 人間だけが編集する / 進行役の参加者の発言から抽出して更新する (小さいモデルでの
   信頼性が論点) / 発言の末尾に構造化した更新ブロックを書かせる。
3. prompt での位置: プロジェクト資料 (TASK-18) と場面設定の間か、リマインダーの直前か。
4. 文脈量: 状態シートの上限文字数。

各案の利点・欠点と推奨を設計書に追記し、実装タスクを切る。検討は同梱プリセットのうち TRPG 卓
(進行役ターン規則のタスクで追加) を想定シナリオにする。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- 設計書 §4.7 に 4 点の案・測定・推奨を記録した。§0・§7 の「chat 単位の JSON 状態」は §4.7 への参照に置き換えた。
- ユーザー判断 (2026-09-22): 起票時の 3 案のうち「場面設定を分ける」案は採らず、共通の状態 (chats.state_sheet) と参加者の状態 (participants.state_sheet) の 2 種にした。状態は参加者個別にも要り、TASK-23 のアクションに付随して変わるという指摘による。更新はモデルではなく、人間の編集とアクションの効果 (set / add) をアプリが適用する形。全参加者に全員分を渡す。
- 測定 (trpg-table の GM prompt を §4.3 どおり再現、temperature 0.25、各条件 5 回): 更新ブロックを書いた回数は gemma-4-e4b 差分形式 0/10、gpt-oss-20b 差分形式 2/10 (項目名は 2 件とも英語化) と全書き直し形式 1/10 (状態が変わる場面、形式ごとに 10 回)。発言からの抽出は測定しておらず、遅延 (§8.1) と精度の根拠が無いことで退けた、場所の移動は両モデルとも 0。シートの値が履歴と食い違うときにシートに従った回数は gpt-oss-20b で 0/15 (3 つの位置のどれでも同じ)。
- e4b はローカル (127.0.0.1) では 1 回 20〜45 秒かかったので差分形式の 15 回で打ち切り、以降は LAN の gpt-oss-20b で測った。e4b の全書き直し形式と位置の比較は未測定。計測スクリプトは使い捨てでリポジトリに置いていない (条件は §4.7.2 に記載)。
- 起票: TASK-35 (列・編集・注入・エクスポート・プリセット)、TASK-36 (アクションの効果の適用。TASK-35・TASK-23 に依存)。前提条件の判定 (持っていない物は使えない) は prompt では担保できないので、TASK-23 で扱う論点として §4.7.2 と TASK-36 に申し送った。
