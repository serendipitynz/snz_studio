## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 背景

TRPG の判定はダイスの出目に依存するが、LLM に「d20 を振れ」と言っても出目は偏り、
物語の都合に合わせた値を返しがちで、判定の公正さが成り立たない。

## このタスクで決めること (実装はしない)

1. 出目の生成元: 人間が介入発言で出目を書く (現状でも可能) / アプリがサーバー側で乱数を生成し
   「system の発言」として履歴に挿入する / 参加者の発言中の `1d20` のような記法をアプリが検出して
   出目を後置する。
2. 履歴上の表現: 出目を誰の発言として保存するか (participant_id なしの system 相当の role が
   要るか)。既存の履歴マッピング (`mapHistoryForSpeaker`) との整合。
3. UI: 介入欄の隣に「ダイスを振る」操作を置くか、記法検出だけにするか。
4. ルール判定 (目標値との比較、修正値) をどこまでアプリが持つか。最小は「出目を公正に出す」だけ。

各案の利点・欠点と推奨を設計書に追記し、実装タスクを切る。最小案 (出目をアプリが生成して履歴に挿入)
で足りるかを先に判断する。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- 設計書に §4.8 (ダイスと判定) を追加し、4 つの論点それぞれについて案・測定・推奨を記録した。§4.7.1 の「アクションの効果」の定義、§4.7.3 の申し送り、§0・§7 の将来の行を §4.8 への参照に更新した。
- ユーザー判断 (2026-09-22): 出目の出どころは発言末尾のスラッシュコマンド `/roll`。人間の介入発言でも参加者の発言でも検出し、アプリが乱数で振る。専用のボタンは置かず、介入欄の補完と発言の下のチップにする。判定の記録は、コマンドを書いた発言の列 (`messages.dice_rolls`) に保存する。判定は目標値との比較まで行い、スクリプト言語 (SillyTavern の STscript 相当) は持たない。
- 判定の記録を別の system 発言にしなかったのは、facilitator_alternating (末尾が参加者以外の発言なら次は進行役) と weighted (末尾が参加者以外の発言なら連続発言の抑制が外れる) の導出を変えてしまうため。
- 測定 (trpg-table を §4.3 どおりに再現、場面設定のダイス規則を差し替え、temperature 0.7、各条件 5 回):
  - コマンドを書いた回数: スラッシュ形式で gpt-oss-20b 10/10、gemma-4-e4b 3/10 (角括弧形式では 10/10 と 1/10)。gpt-oss-20b は 7/10 を独立した行にせず本文の末尾に続けて書き、3/10 は行動の要約が抜けた。
  - 合計 7 (失敗) を渡したときに、GM が「渡りきった」と描写した回数: 合計だけなら 3/10、アプリが「失敗」を付けると 1/10。合計 19 に「成功」を付けた場合は 10/10 が渡りきった。
  - 計測スクリプトは使い捨てでリポジトリに置いていない (条件は §4.8.2 に記載)。
- AC #3: 効果を生むのは効果コマンド (`/add`・`/use`・`/set`) だけとし、`/roll` の成否から効果を自動で導かない。前提条件 (`/use` は値の先頭の整数が 1 以上) は、効果を当てる時点でアプリが状態シートを読んで判定する。TASK-36 はこの範囲に合わせて保留にした。効果コマンドをモデルが書くかは未測定で、TASK-37 の実装後に測ってから着手する。
- 起票: TASK-37 (`/roll` の実装)。TASK-36 に TASK-37 への依存を追加した。
- ドキュメントとバックログだけの変更で、コードは変えていないので go test / lint は実行していない。
