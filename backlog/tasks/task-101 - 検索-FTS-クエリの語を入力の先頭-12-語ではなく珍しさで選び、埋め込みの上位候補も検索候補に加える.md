## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 背景

`search.ToFtsQuery` は `TokenizeSearchTerms(input, 12)` で入力の**出現順に先頭 12 語**を取り、`"語"*` の OR でつないで FTS5 に渡す。開発用 DB (212 チャンク) で 2026-10-11 に実測すると、次の問題があった。

- 語の選び方が位置だけで決まる。依頼文「第3章で、主人公がギルドに入るまでの経緯と、その時に出会った仲間の名前と性格をまとめてください。あと、ギルドマスターの過去についても触れておいて。」では、12 枠に「第」「公」「まで」「時」が入り、「性格」「ギルドマスター」「過去」が漏れる。
- 「ください」は TinySegmenter で「く / ださい」に割れるため、ストップワードの「ください」に当たらず「ださい」が残る。
- 12 語の OR + 前方一致で 212 チャンク中 180 件が一致する。FTS は候補をほとんど絞れておらず、実質的に bm25 の順位付けだけで結果が決まっている。
- 埋め込みは入力全体を見るが、`rankDocumentCandidates` / `rankMemoryCandidates` は FTS 候補を並べ替えるだけで、semantic fallback は FTS 由来の採用件数が limit 未満のときしか動かない。OR 検索では候補がすぐ limit に達するので、語を共有せず意味だけが近い文書・メモリは入らない。

全語を使う案は採らない。速度は許容範囲 (チャンク 50 倍・1,000 字の貼り付けで約 250 ms、通常の依頼文では 30 ms 程度) だが、貼り付けた本文の語が依頼の語を埋もれさせ、結果が本文と語を共有するチャンクに寄る。

## 作業

1. FTS クエリの語を、入力内の位置ではなく文書頻度 (その語を含むチャンク数。`fts5vocab` で引ける) の低い順に選ぶ。上限は 12 を起点に実測で決める。
2. 文書頻度が高すぎる語と、「ださい」のような分かち書きの残骸を落とす。
3. 埋め込みが有効なときは、埋め込みの上位候補を FTS 候補に合わせてから混ぜる (FTS に一致しない候補の FTS スコアは 0)。あわせて semantic fallback の位置づけを見直す。
4. 多人数会話の検索クエリ (`turncontext.go`: 最新発言 → 直前 2 発言 → 場面設定の先頭 200 字) にも同じ変更が効くことを確かめる。

## 影響

- ハイブリッドの配分 (ドキュメント 0.55/0.45、メモリ 0.5/0.5) と fallback の閾値は、今の候補集合のもとで調整されている。候補の作り方が変わると順位が変わるので、実データで手動確認する。
- `docs/multi-agent-chat-design.md` §4.4 は、検索クエリの並び順の理由として「FTS は先頭 12 トークンしか使わない」ことを挙げている。語の選び方を変えるとこの理由が成り立たなくなるので、並び順の扱いとあわせて改訂する。
- TASK-100 (bm25 の列重みのずれ) とは別件。TASK-100 の修正後の重みを前提にする。

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. search: QueryTerms (入力の語を重複なしで取り、ストップワードが分かち書きで割れた残骸 (く+ださい) を隣接語の連結で検出して落とす) と SelectTerms (文書頻度の低い順に選ぶ。頻度 0 の語は枠外で通す、頻度が高すぎる語は落とす、主の語 → 補いの語の順に枠を埋める) と FtsQuery に分ける。TokenizeSearchTerms / ToFtsQuery (先頭 12 語) と、その Node 版とのパリティテストは削除する。
2. 文書頻度は fts5vocab ('row') を migration で document_chunks_fts / memories_fts に張り、前方一致の範囲の doc を合計して引く (上限は総行数)。プロジェクト単位の MATCH 件数は 50 倍コーパス・218 語で 760 ms かかるため採らない (vocab は 30 ms)。
3. retrieval: SearchQuery{Text, Background} を導入。埋め込みが有効なときは、プロジェクトの埋め込みを 1 回走査して FTS 候補の意味スコアを付け、FTS に一致しない上位 K 件 (下限 floor を超えるもの) を FTS スコア 0 で候補に加える。semantic fallback の段は廃止し、その floor を「FTS 外の候補の入場条件」に移す。埋め込み無効時は FTS だけで従来どおり。
4. turncontext: 発言を Text、場面設定の先頭 200 字を Background にする (ユーザー判断 2026-10-11: 発言の語を優先し、余った枠を場面設定の語で埋める。埋め込みには両方を渡す)。
5. 上限 (12 起点) と頻度の閾値を dev DB で実測して決め、テスト (AC1〜4)、docs (§4.4、current-spec en/ja) を更新、実データで順位の変化を確認する。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 実装

- 語の選択 (search.QueryTerms / SelectTerms / FtsQuery): 入力の語を重複なしで取り、文書頻度 (前方一致で含む行数) の低い順に最大 12 語を選ぶ。頻度 0 の語は枠外で通す、半数を超える行に出る語は落とす、本文の語 → 背景の語の順に枠を埋める。TokenizeSearchTerms / ToFtsQuery と、その Node 版とのパリティテスト (terms / ftsQuery) は削除した (Segment / BuildSearchText のパリティは残す)。
- 文書頻度: migration 021 で document_chunks_fts / memories_fts に fts5vocab ('row') を張り、前方一致の範囲の doc を合計して引く (上限は総行数)。
- 候補: 埋め込みが有効なときはプロジェクトの埋め込みを 1 回走査し、FTS 候補に意味スコアを付け、FTS 外で floor を超える上位 (ドキュメントは limit×chunksPerDocument chunk、メモリは limit 件) を FTS スコア 0 で加えて一緒に並べる。semantic fallback の段は廃止し、その floor (ruri 0.9) は FTS 外の候補の入場条件として残した。
- 多人数会話: SearchQuery{Text: 直近 3 発言, Background: 場面設定の先頭 200 字}。2026-10-11 のユーザー判断で「発言の語を優先し、余った枠を場面設定の語で埋める。埋め込みには両方」。

## 判断の理由

- 文書頻度をプロジェクト単位の MATCH 件数で取る案は採らなかった。開発 DB を 50 倍にした 10,600 チャンクで、1,000 字の貼り付け (218 語) が MATCH では 760 ms、fts5vocab では 30 ms だった。fts5vocab は全プロジェクト通算になる。bm25 の IDF も全行の統計なので、ずれはしない。
- 頻度の閾値は当初 25% で試したが、実データで「デルヴァン (57%)」「ナシェル (51%)」に加えて「最初 (27%)」まで落ちた。FTS5 の bm25 は半数を超える行に出る語の IDF を 0 (1e-6 に固定) にし、そうした語は行を拾うだけで順位に効かない。これを根拠に閾値を 50% にした。主要人物名は旧クエリでも順位には寄与していなかった。10 行未満の表 (少数のメモリ) では落とさない。
- 上限 12 語: 閾値後に残る語は、短い依頼文 3 件で 5〜7 語。依頼文の例では 15 語残り、13 語目以降は「あと / 章 / まで」になる。上限 24 にすると「まで」が入り、AC#1 に反する。長い入力 (貼り付け・多人数会話) では、出現 1〜2 件の語が 12 枠を占め、FTS の一致は 1〜3 chunk に絞られる。その分は常に加わる埋め込み候補が補う。
- 分かち書きの残骸: 「く / ださい」に加えて「てく / ださい」「でく / ださい」の割れ方があり、隣接 2 語の連結では拾えなかった。そこで、3 文字以上のストップワード (ですか / ますか / ください / お願いします) が語の境界をまたぐ箇所を削る方式にした。2 文字のストップワードは「うそ / の」の「その」のように実在語を削るので対象外。

## 計測 (開発 DB、ruri-v3-30m、2026-10-11)

- 依頼文の例: FTS 一致 175 → 104 chunk。「性格」「過去」が入り、「第」「時」「まで」「ださい」が外れた。
- 「デルヴァンとナシェルが最初に対立した理由は何だった？」: 176 → 145。上位 4 件の文書は同じ。
- 貼り付け (第 5 章冒頭 1,000 字 + 続きを書いて): 199 → 1。1 位の第 5 章は変わらない。2〜4 位は、FTS の一般語で拾われていた第 13 / 12 / 14 章から、埋め込み候補の本文運用メモ / 基礎ルール / 第 9 章に替わった。
- 多人数会話 (トーク with doc の発表会、開幕・1・5・11 発言後): ターンごとに FTS の語が入れ替わり、場面設定の語は開幕ターンにだけ入る。この 12 chunk のプロジェクトでは文書の順位は変わらない。
- BenchmarkRetrievalLargeDocument/SearchDocuments: 21.0 ms → 17.7〜20.5 ms。埋め込みの走査は毎回走るようになったが、本文を読まなくなった分で相殺した。

## 手で見てほしいもの

- ドキュメント 0.55/0.45・メモリ 0.5/0.5 の配分と ruri の floor 0.9 は変えていない。ruri の意味スコアは 0.89〜0.95 に固まる。そのため FTS 外の候補 (最大 0.45×0.95 ≒ 0.43) が上回れるのは、正規化後の FTS スコアが低い候補だけになる。配分を見直すかは、大きいプロジェクトで使ってから判断してほしい。
- 大きいプロジェクト (原稿 1 MB 級) で、長い多人数会話のターンに FTS が拾う資料は確かめていない。
- fts5vocab 非対応の sqlite3 CLI (Android SDK 同梱版など) では、vocab 表を読むクエリが「no such module」になる。他の表は読める。
