# 多人数会話機能 — 事前検討の記録

ステータス: **記録（2026-09-09 確定）** / 対象: [multi-agent-chat-design.md](./multi-agent-chat-design.md) の背景資料

> 目的: 「LAN 上の複数 LM Studio を使い、AI 同士にディベート・即興劇・TRPG をさせる」構想の
> 実現可否を検討したセッションの結論を、snz_studio への組み込み設計の前提として残す。
> 用語（参加者・ターン進行ルール・ターンエンジン・多人数会話）の定義は設計書 §2 に置き、本書もそれに従う。

---

## 1. 動機と実行環境

LAN 上の 3 台に LM Studio を導入済みで、これらを束ねて AI 同士の会話をさせたい。

| マシン | 主なモデル | 備考 |
| --- | --- | --- |
| 自作 PC（RTX 5060 Ti 16GB） | gpt-oss-20b | ほぼ常時ロード |
| MacBook Pro M5 32GB | gemma 12B 級 | |
| MacBook Air M2 24GB | gemma E4B 級（実効 4B） | |

LM Studio は OpenAI 互換 API（既定 `http://<マシンIP>:1234/v1`）を提供し、
サーバー設定「Serve on Local Network」で LAN 内の他マシンから呼べる。
したがって実装の本体は「複数エンドポイントをターン制で呼ぶ HTTP ループ」に帰着する。

## 2. ユースケース別の実現性

### 2.1 ディベート — 実現可能

- 構成: 肯定側・否定側にモデルを割り当て、ターン制で発言させる。審判・司会は最強モデル。
- 品質の要点（小型モデルの既知の弱点と対策）:
  - 放置すると互いに同意して収束する → 毎ターンの役割リマインド
    （「同意で終わらない」「相手の主張の弱点を必ず 1 つ指摘」）をシステムプロンプトに焼き込む。
  - 履歴が伸びると役割を忘れる → 履歴を要約で圧縮して渡す。

### 2.2 TRPG — 実現可能だが難度は一段上

- GM 役 + プレイヤー役の構成。GM が最も知力を要するので最強モデルを充てる。
- ディベートに無い難所と対策:
  - HP・所持品・フラグ等の状態を LLM の記憶（会話履歴）に任せると破綻する
    → 状態はアプリ側が JSON で保持し、毎ターンプロンプトへ注入。モデルは語りと行動宣言だけを担う。
  - LLM にダイスを振らせると都合のよい目を出す → 乱数はコードで振る。
    判定の要否・難易度は GM に構造化出力（JSON）で宣言させ、結果を次のプロンプトへ渡す。
  - D&D 5e 級のルールの正確な運用は 20B 級でも怪しい → 軽量な自作ルール、またはコード側での裁定に割り切る。
- 人間が プレイヤーの一人として参加する形（人間 1 人 + AI パーティ）も同じループで成立する。

### 2.3 即興劇 — 3 つの中で最も容易

- 状態管理・ルール裁定・乱数がすべて不要。必要なのは会話履歴とキャラ設定だけ。
- 弱点は「Yes, and」の and（相手の設定を受けて新要素を足す）が弱いこと
  → 「毎ターン、シーンに新しい事実を 1 つ追加せよ」の指示 + 演出家役による転機注入の二段構え。
- 発言順を固定巡回でなく指名制にできると舞台らしくなる。幕切れは演出家役に宣言させる。

## 3. モデル評価の見立て

| モデル | 見立て |
| --- | --- |
| gpt-oss-20b | ディベーター・審判・GM・演出家いずれも十分。この構成の主砲 |
| gemma 12B 級 | ディベーター・プレイヤー役として実用ライン。役割維持が安定 |
| E4B 級（実効 4B） | ディベートでは反駁が浅くボーダー。即興劇・性格の濃い脇役では健闘。役割リマインド + 履歴要約 + 短いターン制限（例: 200 字以内）で補正。日本語は英語比で一段落ちる |
| 2B 級以下 | 数ターンで反復・同調・逸脱。生産的な会話は期待できない |

異種モデルの混成は、口調・発想の多様性としてむしろプラスに働く。

## 4. 先行事例

- **ディベート系 OSS**（多数あるが小規模個人プロジェクトが中心）:
  [ai-debate-arena](https://github.com/rd-serendipity/ai-debate-arena)（Streamlit、複数モデル対戦 + 採点）、
  [Deb8flow](https://github.com/iason-solomos/Deb8flow)（LangGraph、司会 + 審判 + ファクトチェック）ほか。
  多くはクラウド API 前提だが、OpenAI SDK 利用のものは base_url 差し替えで LM Studio に向けられる。
  ラウンド構成・審判プロンプトの参考元として有用。
- **汎用の多人数会話フレームワーク**:
  [Microsoft AutoGen](https://github.com/microsoft/autogen) の GroupChat が代表
  （発言者選択 `round_robin` / `random` / `auto` / `manual` + カスタム選択関数 + FSM 遷移制約）。
  ただし依存が重く API も流動的だった経緯があり、今回の規模では不採用。素の HTTP ループで足りる。
- **完成アプリ**: [SillyTavern](https://github.com/SillyTavern/SillyTavern) のグループチャット +
  [ST-Multi-Model-Chat 拡張](https://github.com/CATIOR/st-multi-model-chat)（キャラごとに別接続先を自動切替）。
  コードを書かずに 3 台構成の会話品質を体験検証する用途に向く。審判・ダイス等の進行ロジックは守備範囲外。
- **TRPG 関連**: AI Dungeon（単一モデルの古典）、CALYPSO（LLM による GM 支援の研究）。
  「できるか」は実証済みで、争点は手元モデルでの品質のみ。

## 5. 結論

1. 単独の新規アプリは作らず、**snz_studio に組み込む**。
   呼び出しごとの接続先上書き（`resolveTarget` / `CompletionTarget`）、SSE ストリーミング、
   メッセージ永続化、モデル確認系（`ListModels` / `EnsureModelLoaded` / `CheckConnection`）が既にあり、
   土台の 6〜7 割が流用できるため。
2. ディベート・即興劇・TRPG を個別機能にせず、
   **役割プロンプト + ターン進行ルールを差し替え可能な多人数会話エンジン 1 つ + プリセット（データ）**で実現する。
3. 段階分け: まず参加者 + ターンエンジンだけで成立するディベート・即興劇から。
   TRPG の状態管理・ダイス・構造化出力は第 2 段階に回す（既存構造への変更が最小で済む順序）。

設計の本体は [multi-agent-chat-design.md](./multi-agent-chat-design.md)。
