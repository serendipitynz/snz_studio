## 0. ゴールとスコープ

- 1 つの chat の中で、**接続先の異なる複数のモデルが役割を持って発言し合う**。発言はストリーミング表示され、既存の messages として永続化される。
- ディベート・即興劇などの用途は**個別機能にしない**。エンジンは 1 つで、用途差はプリセット（§6、= データ）で表現する。
- **TRPG の再現を用途の一つとして目標に含める**（2026-09-21、TASK-20）。ここで言う TRPG の再現とは、参加者の 1 人が GM として
  シナリオ（ダンジョンの構造・NPC の真意・伏線）を知り、他の参加者がそれを知らないまま行動する会話が成り立つことを指す。
  参加者ごとにプロジェクト資料を渡すかを選べること（§4.4）がその最小の道具立てである。
  状態管理（キャラクターシート・ダイス・構造化出力による判定）は引き続き非ゴールで、§7「将来」に置く。
  ただし刻々と変わる状態の置き場は TASK-22 で設計し（§4.7、未実装）、実装は TASK-35・TASK-36 に切ってある。
  ダイスと判定も TASK-23 で設計し（§4.8、未実装）、実装は TASK-37 に切ってある。
- **非ゴール（今回やらない）**: TRPG の状態管理（キャラクターシート・ダイス・構造化出力による判定）、進行役による指名（進行役がモデル出力で次の話者を選ぶこと）、複数マシンの並列生成。いずれも将来拡張（§7・§8）。
  決定的に進行役を挟むターン進行ルール（`facilitator_alternating`、§4.5）は 2026-09-22 の TASK-21 で入れた。モデル出力を読まないので、上の非ゴールには当たらない。
  発言本文の呼びかけを読む `weighted`（§4.6）は 2026-09-22 の TASK-34 で入れた。モデル出力を読むが、読むのは進行役に限らず
  どの参加者の発言でも人間の介入発言でも同じで、読んだ結果は次の話者を決める 3 つの係数の 1 つにすぎない（§4.6.8）。
  上の非ゴールが指すのは「進行役が」次の話者を選ぶ規則なので、`weighted` はこれに当たらない。
  retrieval（documents / memories）との統合は起票時の非ゴールだったが、TASK-18 で方針転換して §4.4 のとおり取り込んだ。

AGENTS.md の Constraints（local-only / single-user / no heavy real-time architecture / no over-engineering）は維持する。LAN 上の LM Studio は「外部インフラ」に当たらない（既存の外部 LLM エンドポイント方式と同じ扱い）。

## 2. 用語とドメインモデル

- **参加者**とは、多人数会話に属する「表示名 + 役割プロンプト + 接続先 base URL + モデル名」の設定の組を指す。
- **役割プロンプト**は、参加者ごとにモデルへ system メッセージとして渡す、人格・立場・口調・行動規則を指示する文字列。
- **多人数会話**とは、参加者を 2 つ以上持ち、発言生成をターンエンジンが担う chat を指す。既存の単独 assistant の chat と同じ `chats` テーブルに保存し、種別列 `kind` で区別する。
- **ターン**は、ターン進行ルールで選ばれた 1 人の参加者が、モデル呼び出し 1 回分の発言を生成し `messages` に保存されること。
- **ターン進行ルール**（`turn_rule`）は、次に発言する参加者を決める規則。現在 4 種:
  - `round_robin`: 参加者の登録順（`sort_order`）を循環。直近の参加者発言から次を導くため、サーバー側に進行状態を持たない。
  - `manual`: リクエストで参加者を指名。
  - `facilitator_alternating`（2026-09-22、TASK-21）: 進行役と進行役以外の参加者が 1 発言ずつ交互に話し、
    進行役以外は `sort_order` 順に循環する。これも保存済みの発言だけから導く（§4.5）。
  - `weighted`（2026-09-22、TASK-34）: 編成の参加者ごとに係数の積で重みを求め、最大の参加者が話す。
    呼ばれた参加者と長く黙っていた参加者が先に話し、同じ参加者は続けて話さない。これも保存済みの発言
    （と、発言に保存した呼びかけ先）だけから導く（§4.6）。
- **進行役**とは、`facilitator_alternating` において他の参加者 1 人ごとに必ず 1 回発言する位置に置かれる、
  名簿上の参加者 1 人を指す。chat が `facilitator_participant_id`（§3）で 1 人を指名する。
  `weighted` も同じ設定を読み、進行役を直近発言の抑制（§4.6.1）から外す。`weighted` では進行役は任意で、
  居なければ誰も外さない。
  §7「将来」の**進行役による指名**（進行役がモデル出力で次の話者を選ぶ規則）とは別物で、
  `facilitator_alternating` は決定的であり、モデルの出力を読まない。
- **ターンエンジン**（`TurnEngine`）とは、ターン進行ルールに従い参加者のモデル呼び出しと発言保存を繰り返す Go サービスを指す。
- **場面設定**（`scene_prompt`）とは、多人数会話の全参加者のシステムプロンプトに共通して前置される chat 単位の文字列（論題・シーン・世界観など）を指す。
- **プリセット**とは、参加者一式・ターン進行ルール・場面設定の雛形をまとめた、多人数会話に適用できるデータを指す。適用できるのは新規作成時と、発言がまだ 1 件も無い多人数会話に対してである（§5）。

## 3. スキーマ（migration 10〜15）

```sql
ALTER TABLE chats ADD COLUMN kind TEXT NOT NULL DEFAULT 'assistant';       -- 'assistant' | 'multi_agent'
ALTER TABLE chats ADD COLUMN turn_rule TEXT NOT NULL DEFAULT 'round_robin'; -- multi_agent のみ意味を持つ
ALTER TABLE chats ADD COLUMN scene_prompt TEXT NOT NULL DEFAULT '';

CREATE TABLE participants (
  id           TEXT PRIMARY KEY,
  chat_id      TEXT NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
  display_name TEXT NOT NULL,
  role_prompt  TEXT NOT NULL,
  base_url     TEXT NOT NULL,
  model_name   TEXT NOT NULL,
  sort_order   INTEGER NOT NULL DEFAULT 0,
  created_at   TEXT NOT NULL,
  deleted_at   TEXT                    -- NULL = 編成に在籍。非 NULL = 除籍済み（過去の発言の帰属だけ残す）
);

ALTER TABLE messages ADD COLUMN participant_id TEXT; -- NULL = 従来の user / assistant 発言
```

migration 11（2026-09-21、TASK-20）と、その列を改称した migration 12（2026-09-21、TASK-32）:

```sql
ALTER TABLE participants ADD COLUMN receives_background INTEGER NOT NULL DEFAULT 1;
ALTER TABLE participants RENAME COLUMN receives_background TO receives_project_material; -- 1 = プロジェクト資料を渡す
```

migration 14（2026-09-22、TASK-21）:

```sql
ALTER TABLE chats ADD COLUMN facilitator_participant_id TEXT NOT NULL DEFAULT ''; -- '' = 未指定
```

- `facilitator_participant_id` は `facilitator_alternating` が挟む進行役（§2）の participant id。
  ターン進行ルールの付随設定であって 2 本目の規則列ではないので、`round_robin` に戻しても値は残り、
  戻し直すときに選び直さずに済む。
- 外部キーは張らない。指した参加者は除籍できるため、**指し先の消えた id と未指定は同じ場合**として扱い、
  どちらもターンは `round_robin` の導出に落ちる（§4.5）。除籍時にこの列を消す処理は持たない。

migration 15（2026-09-22、TASK-34）:

```sql
ALTER TABLE messages ADD COLUMN addressed_participant_ids TEXT NOT NULL DEFAULT '[]'; -- JSON 配列。'[]' = 呼びかけ無し
```

- 発言が呼びかけた参加者 id の集合（§4.6.5）。発言の保存時に確定し、以後は本文から導き直さない。
- 結合テーブルではなく JSON 配列の列にするのは、集合が発言と一緒に丸ごと読まれるだけで、単独で引かれることが無いため。
  指した参加者は除籍できるので、`facilitator_participant_id` と同じく外部キーは張らない。

migration の id（`011_participant_receives_background`）は改称しない。id は `schema_migrations` に記録される値なので、
変えると導入済みのデータベースが 11 を再実行し、既にある列に対して `ADD COLUMN` を当てて失敗する。

- **「プロジェクト資料を渡す」**（`receives_project_material`）とは、その参加者が話者になるターンでプロジェクト資料（§4.4）を組み立てて system prompt に入れ、
  参照として保存することを指す。既定は 1 で、`DEFAULT 1` により migration 11 より前からある参加者も渡す側になる。
- 参加者の発言は `role = 'assistant'` + `participant_id` で保存する。表示名・モデル名は participants を引く（`model_name` 列には従来どおり実際に使ったモデルも記録する）。
- 人間の介入発言（論題の追加投入・野次など）は従来どおり `role = 'user'`・`participant_id IS NULL`。
- 既存 chat は `kind = 'assistant'` のまま一切影響を受けない。
- **参加者の除籍は論理削除**（`deleted_at` を立てる）とし、行は消さない。`messages.participant_id` には
  意図的に外部キーを張らない（既存 `messages` への `ALTER TABLE` を最小に保つため）が、行が消えないので
  過去の発言の表示名は常に解決できる。
  **Why**: 物理削除にすると、(1) 過去の発言の `participant_id` が解決不能になり観戦ビューが表示名を失う、
  (2) `round_robin` の「直近の参加者発言 → 次」が起点を失って次の発言者が決まらない。
  いずれもデータが壊れるのではなく既存の履歴の読み方が壊れるので、除籍は在籍フラグで表す。
- したがって参加者の集合は 2 種類ある。**編成**（`deleted_at IS NULL`、`round_robin` の巡回対象・編成パネルの表示対象）と、
  **帰属解決用の全行**（表示名・モデル名の解決対象）。repository 層は両者を別メソッドで返す。
- `participant_id` は同一 chat の participants しか指さない。ただし ID の解決範囲はルートの形で決まるので、
  検証の意味があるのは chat がルートに現れる操作だけである:
  - `POST /api/chats/{chatId}/turns/stream` の `manual` 指名: `chatId` と `participants.chat_id` の
    一致をサービス層で検証し、他 chat の参加者を指名したら 404。ここは比較対象が 2 つあるので本当の検証になる。
  - `PATCH` / `DELETE /api/participants/{participantId}`: 対象の chat はその参加者自身の `chat_id` で決まり、
    比較相手が無い。よって「同一 chat か」を問う余地はなく、存在しなければ 404 とするだけでよい。
    **Why**: これは既存の API 規約に合わせた結果である。既存ルートも、作成は親配下
    （`POST /api/projects/{projectId}/memories`）、更新・削除は自身のフラットな ID
    （`DELETE /api/memories/{memoryId}` / `PATCH /api/documents/{documentId}/category`）で統一されている。
    単一ユーザー・認証なし（AGENTS.md Constraints）なので、ここに越えるべき権限境界も無い。

## 4. ターンエンジン（`internal/service/turnengine.go`）

### 4.1 1 リクエスト = 1 ターン

サーバー側に常駐の進行ジョブを持たない。1 回の API 呼び出しが 1 ターンを実行して SSE で流し、
連続進行（自動進行）はフロントエンドが次ターンの呼び出しを繰り返すことで実現する。
**Why**: 常駐ジョブとその状態管理を持たずに済み、AGENTS.md の「No heavy real-time architecture」に収まる。
自動進行の停止 = フロントが次のターンを呼ばないこと。

**ターンは HTTP リクエストの寿命に縛られない**（既存 SSE 経路の実際の挙動）。
`CreateChatCompletionStream` は呼び出し元の `context` ではなく `context.Background()` +
チャンク到着ごとに延びるスライディング期限で動き（[llmclient.go](../internal/service/llmclient.go)）、
SSE の書き込み失敗も無視される（[handlers.go](../internal/httpapi/handlers.go) の `_ = sse.Event(...)`）。
つまり進行中のターンは、クライアントが切断してもモデル生成を完走し `messages` に保存される。
本設計はこれを**仕様として受け入れる**:

- 停止できる粒度はターン境界のみ。「自動進行の停止」は進行中のターンを中断しない。UI もそう表示する。
- 切断・リロード後の復帰は、`messages` を読み直すこと（完走したターンはそこに入っている）。
  取りこぼした delta を再送する仕組みは持たない。
- 生成の中断が必要になったら、`TurnEngine` と `LLMClient` に呼び出し元 `context` を通す変更が前提になる
  （既存の単独 assistant チャットにも影響する変更なので、本設計の範囲外・§7 将来）。

### 4.2 ターンの処理手順

0. **その chat のターン実行権を取る**（chat 単位の in-process な排他。取れなければ 409 を返して終了）。
   **Why**: 発言者の決定は「`participant_id` を持つ直近メッセージ」を読んで行い、その結果が `messages` に入るのは
   ターン完了時（手順 5）。よって重なった 2 リクエストは両方とも同じ直近メッセージを読み、同じ参加者を選んで
   二重に発言させる。自動進行はフロント側のループなので（§4.1）、「1 ターン進める」の連打や
   自動進行と手動指名の競合で現実に重なる。単一ユーザー・単一プロセスなので `sync.Mutex` の
   `TryLock` 相当で足り、DB 側の予約列は要らない。
1. ターン進行ルールで発言者を決定（`round_robin`: `participant_id` を持つ直近メッセージ → 編成（`deleted_at IS NULL`）の `sort_order` 順の次。直近発言の参加者が除籍済みで巡回位置が定まらないときは編成の先頭から。`manual`: リクエストの `participantId` 必須。`facilitator_alternating`: §4.5。`weighted`: §4.6.1）。
2. `EnsureModelLoaded` / `CheckConnection` で接続先を確認。確認もエラー文も `resolveTarget` で解決した後の
   接続先・モデル（= 手順 4 が実際に使う組み合わせ）で行う。**Why**: 参加者は接続先とモデルを空欄にすると
   ワークスペース設定をフィールドごとに独立して継承するので、参加者の生の値で確認すると、継承した側が
   空文字のまま渡り（`EnsureModelLoaded` は空のモデル名を常に拒否する）、エラー文も継承した側が空白になって
   何を試して失敗したのか読めない。失敗はターンをエラーで返す（他の参加者へのフォールバックはしない）。
   確認を通ったら、選んだ話者を SSE の `speaker` イベントで通知する（§4.6.6）。
3. プロンプトを組み立てる（§4.3）。
4. `CompletionTarget{BaseURL, Model}` を渡して `CreateChatCompletionStream` を実行、delta を SSE 転送。
5. 完了した発言から呼びかけ先を検出し（末尾の指示子はここで剥がす、§4.6.5）、`messages` に保存
   （`participant_id`・`model_name`・`addressed_participant_ids`・既存の生成メトリクス列）。

### 4.3 プロンプト組み立て

OpenAI 互換 API には「多者会話」のロールが無いため、発言者本人の視点へ写像する（先行事例で一般的な手法）:

- `system` = プロジェクト資料（§4.4）+ 場面設定 + その参加者の役割プロンプト + 参加者一覧 + 役割リマインド。
  役割リマインドは毎ターン付与する固定文（「あなたは<表示名>としてのみ発言する」「直前の発言に同意だけで終わらない」等）。
  **Why**: 小型モデルは履歴が伸びると役割を忘れ、同意で収束する（検討記録 §2）。
  プロジェクト資料を先頭に置くのは、話し方を決める場面設定と役割が、リマインドの直前で最後に読まれる位置に残るようにするため。
- 履歴の写像: 自分の過去発言 → `assistant`、他参加者と人間の発言 → `user`（内容を「<表示名>: <本文>」に整形）。
- **プロンプトの末尾は、その参加者が答えるべき直前の発言にする**。`LLMClient` が常に末尾へ置く user メッセージ（§1）に、
  写像した履歴の最後の発言をそのまま入れる。「次はあなたの番です」の進行文で終わらせるのは、答えるべき発言が無いとき
  （最初のターン、および `manual` で直前と同じ参加者を指名したとき）だけにする。
  **Why**: 推論してから答えるモデルは、末尾の進行文を「会話への指示」と読んで発言してよいかを推論し続け、
  内容を返さないことがある。内容が空のターンは保存できないので失敗になる。同梱の 20 の扉 + gemma-4-e4b で計測すると
  （2026-09-19）、進行文を末尾に置いた場合は 4 回中 2 回が空、残りも 1 語の回答に 184〜454 トークンを費やした。
  質問を末尾に置くと 4 回中 4 回が 6 トークンで正しく答えた。
- 履歴は直近 30 発言に制限する（定数 `turnHistoryLimit`）。要約による圧縮は行わない（理由は §8「実装で解消した判断」）。
- 役割リマインドの内容（Phase C で確定）: 「自分としてのみ発言し、他の参加者の発言や動作を代筆しない・1 発言に複数人分を入れない」
  「発言の先頭に名前や記号を付けない」「直前の発言のどこに反応しているかが分かるように述べ、同意だけで終わらない」
  「発言の長さは場面設定の指定に従う」。それぞれ小型モデルで実際に見えた崩れ方（履歴の「<表示名>: 本文」形の模倣、
  複数人分の生成、同調、長さ指定の忘却）への対処で、プリセット側には書かない。
  `weighted` のときだけ、これに「次に話してほしい相手がいるときだけ、発言の最後の行に `[次: 表示名]` と書く」を足す（§4.6.5）。
  他の 3 規則は呼びかけを読まないので、書かせても使われない名指しを誘うだけになる。既存規則のプロンプトを変えないためにも足さない。

### 4.4 既存 chat フローとの分離と、プロジェクト資料の取り込み

既存の `service/chat.go`（単独 assistant 用の応答生成）と `ContextService.Assemble`（その文脈組み立て）には
手を入れず、ターンエンジンは独立したサービスにする。共有するのは LLMClient・repository 層・RetrievalService と、
`ContextService` に足した多人数会話専用の組み立て関数 `AssembleTurnMaterial`
（[turncontext.go](../internal/service/turncontext.go)）。`kind = 'multi_agent'` の chat に対する
既存の応答生成ルート（`POST /messages` / `/messages/stream`）は、生成を行わずユーザー発言の保存のみ行う（人間の介入発言用）。

「プロジェクト資料」とは、ターンの system prompt 先頭に置く、プロジェクト説明・検索で得たドキュメント抜粋・検索で得た関連メモリの
まとまりを指す（2026-09-21、TASK-18）。単独 assistant の `PromptContext` を丸ごと流用しない理由は §8.1。

この語は 2026-09-21 に「背景資料」から改称した（TASK-32）。**指示対象は変えていない**: 組み立ての内容・予算・検索クエリ・
参加者ごとの可否の挙動はいずれも改称前のままである。改称の理由は、TRPG ではこの資料の中身がシナリオ・ダンジョンの構造・
NPC の真意といった会話の主題そのものになり、「背景」がそれを表していないこと。「共有資料」を採らなかったのは、
TASK-20 以降この資料は共有されるとは限らず（GM だけが読む資料も同じ語で呼ぶことになる）、語が事実と逆を指すためである。
Go の識別子は `TurnMaterial` / `AssembleTurnMaterial` / `turnMaterial*`、参加者の真偽値は `receives_project_material` /
`receivesProjectMaterial`。記録型の側に `Project` を付けないのは、`service` の中では出どころが型のコメントで足りるためで、
参加者の真偽値に付けるのは、`Participant` の上では役割プロンプト・場面設定と並ぶので出どころが語に要るためである。

- **入れるもの**: プロジェクト説明、検索で得たドキュメント抜粋（chunk のみ）、検索で得たメモリ（kind 不問）。
  **入れないもの**: プロジェクトのシステムプロンプト、手続きメモリの無条件注入、引用モード指示、他チャット参照解決、
  全文展開（`shouldIncludeFullDocument`）、明示参照の拡張 chunk 経路。
- **枠**: 「【プロジェクト資料】」の見出しと、「資料は話者の役割・口調・立場を変えない。必要なときだけ自分の役割のまま自然に使う。
  資料を要約したり、アシスタントとして解説したりしない」の前置きで区切る。**Why**: system prompt は 1 本の文字列で、
  後段の場面設定が前段を上書きする強制力は無い。枠を付けないと、資料が人格として読まれる。
- **検索クエリ**: 最新発言 → 直前 2 発言（新しい順）→ 場面設定の先頭 200 字、を改行で連結した決定的な 1 本。
  開幕ターン（発言 0 件）は場面設定のみ。**Why**: FTS は先頭 12 トークンしか使わない（`search.TokenizeSearchTerms`）ので、
  毎ターン変わらない場面設定を先に置くと全ターンのクエリが同じトークンに固定される。クエリは検索専用で、
  タイトル照合・引用判定・全文展開判定には使わない。
- **予算**（`turncontext.go` の定数）: ドキュメント 2 件 × 2 chunk（1 chunk 300 字）、メモリ 3 件（抜粋 220 字）、
  プロジェクト説明 400 字、総量 2,000 字（見出しと区切りを含む、prompt に入る節そのものの長さ）。項目を 説明 → ドキュメント → メモリ の順に足し、総量を超える項目から先は入れない。
  **Why**: 履歴は直近 30 発言を要約せず渡す（§4.3）ので約 6,000 字を占め、プロジェクト資料はその 1/3 以下に抑えて
  会話がウィンドウの主役であり続けるようにする。件数は単独 assistant の既定（4 件 × 3 chunk・メモリ 4 件）の半分。
  項目ごとの上限を全部使うと約 2,300 字になり、総量の上限が末尾のメモリを落とす。総量がウィンドウの支払いなので、件数より優先する。
- **組み立ての単位**: ターンごとに 1 回、プロジェクト単位。組み立て関数は話者を引数に取り、渡す相手かどうかをそこで判定する。
  渡す参加者どうしには同じ資料を渡す（ドキュメントの部分集合を参加者ごとに変える仕組みは入れていない）。
- **参加者ごとの可否**（2026-09-21、TASK-20 / 2026-09-22、TASK-31）: 参加者は「プロジェクト資料を渡す」の真偽値
  （`receives_project_material`、§3）を持つ。渡さない参加者が話者のターンでは、**共通プロジェクト資料**だけを渡す。
  **共通プロジェクト資料**とは、話者がプロジェクト資料を渡す設定かどうかに関わらず渡すプロジェクト資料の部分集合を指し、
  ドキュメント・メモリの `shared_with_all`（「全参加者に渡す」）が真の行がそれに当たる（TASK-31 で導入、migration 13）。
  **Why**: TRPG の実際の卓では、ルール・世界観・用語集は全員が知っていて、シナリオだけ GM が持つ。
  TASK-20 の 2 値だけでは、プレイヤー役が共有前提の資料まで読めなくなっていた。
  - 絞り込みは**検索の前**（SQL 側、`MaterialScope`・`internal/service/retrieval.go`）で行う。
    **Why**: ターンの予算は 2 件 × 2 chunk とメモリ 3 件しかなく、検索後に落とすと、渡らない行が選択枠を食い切って
    共通のものが 1 件も残らないターンが出る。
  - 渡さない参加者のターンには**プロジェクト説明も入れない**。**Why**: 説明は人間向けに書くもので、
    伏せている当のものを名指しすることがあり、その一部だけを共通と見なす印も無い。
  - **予算は §4.4 の定数のまま**、共通だけのターン用に別枠を持たない。**Why**: prompt の形も履歴の長さも変わらないので、
    ウィンドウの支払いが同じであり、別の数字を置く根拠が無い。
  - 共通に該当する行が無ければ結果は空で、TASK-20 と同じ「何も渡らないターン」になる。
- **「全参加者に渡す」はカテゴリから導出しない**（2026-09-22、TASK-31）: `shared_with_all` はドキュメント 1 件につき
  明示の真偽値 1 つで、既定は偽。カテゴリ（world / rule / index …）からの導出も、登録時の初期値の提案も行わない。
  **Why**: ドキュメント登録画面はドラッグ&ドロップとファイル選択だけでカテゴリの入力欄が無く、登録時のカテゴリは常に
  `doccategory.Infer` の推定値である（ファイル名・タイトル・本文の正規表現一致、どれにも一致しなければ `misc`）。
  そこから初期値を作ると、plot の文書が world と推定された 1 件でシナリオがプレイヤーに渡り、推定が外れていることは
  画面に出ないので渡ったことにも気付けない。既定を偽にするのも同じ理由で、真側から始めると本機能を入れた瞬間に
  TASK-20 が意図的に伏せた資料が流れ始める。カテゴリを人間が選ぶのはドキュメント詳細モーダルだけで、
  そこには「全参加者に渡す」のチェックボックスが同じ画面に並ぶので、提案の余地が無い。
- **メモリも同じ真偽値を持つ**（2026-09-22、TASK-31、ユーザー判断）: `memories.shared_with_all`。
  ただし**新規作成時の既定は `source` から決める**: `multi_agent`（多人数会話の発言から保存したもの、TASK-19）は真、
  それ以外（`manual` / `chat` / `organized`）は偽。migration 13 は既存行にも同じ規則を当てる。
  **Why**: このアプリの多人数会話には他の参加者に見えない発言が無いので、発言から作ったメモリは全員が見聞きした内容であり、
  伏せても隠せるものが無い。手動追加・単独チャットからの抽出・organizer の書き換えは会話の場で発話されたことが一度も無いので、
  人間が明示するまでは閉じたままにする。`source` は記録された事実であって推定ではないため、
  カテゴリからの導出を退けた上の判断とは矛盾しない。memories の `kind`（semantic / procedural / episodic）は
  内容の種類であって公開範囲ではないので、判断には使わない。
  **organizer による書き換えは共有を落とす**: `MemoryRepository.UpdateMemory` は `shared_with_all` を 0 に戻す。
  **Why**: organizer はロックされていないメモリを、他のメモリ（共有していないものを含む）を畳み込む形で書き換える。
  フラグを残すと、共有メモリが伏せたメモリの内容を抱えて戻り、隠していた相手にそのまま届く。
  落として困るのは人間が 1 クリックで戻せる共有の判断だけで、漏れた側は取り返しがつかない。
- **既知の制約**: 参加者の追加時の既定値は「渡す」で、migration 11 より前からある参加者も `DEFAULT 1` で渡す側になる。
  したがって隠し情報を作るには、隠す相手を明示的に「渡さない」にする操作が要る。
  また、渡す参加者どうしでは資料を分けられないので、「設計者は要件と設計書、レビュアーはそれに加えて規約」のように
  参加者ごとに異なる部分集合を読ませる用途は真偽値では表現できない。必要になった時点で、参加者 → ドキュメント ID の集合を
  持たせる拡張を別に切る（メモリを参加者ごとに絞る必要も、その時点で判断する）。
- **参照の保存と表示**: prompt に入れた項目と保存する参照は同じ最終選択から作る（`TurnMaterial`）。参加者発言は
  `role = assistant` + `participant_id` なので `assistant_message_references` をそのまま使い、多人数会話画面は
  単独 chat と同じ `MessageReferences` で「使用した参照 (N)」を折りたたみ表示する。
  発言と参照は `ChatRepository.AddMessageWithReferences` で 1 トランザクションに保存する。
  **Why**: 別々に保存すると、参照の保存だけ失敗したターンが「失敗」として返る一方で発言は transcript に残り、
  round_robin がその話者を飛ばす。
- **検索失敗**: ドキュメント検索・メモリ検索がエラーを返したら、ターンはプロジェクト資料なしで続行し、ログ
  （`[turn] project material unavailable`）に残す。その発言に参照は保存しない。**Why**: 自動進行中に検索が壊れると毎ターン止まる。
  埋め込みエンドポイントの失敗はここに含めない: `EmbeddingClient` は自身を無効化してキーワード検索で続行する
  （単独 chat と同じ縮退）ので、プロジェクト資料も参照も通常どおり付く。

読む方向（ドキュメント・メモリ → 会話）に対し、書く方向（会話 → プロジェクトのメモリ → 後続のチャット・多人数会話）は
**発言のメモリ保存**だけにする（2026-09-21、TASK-19）。「発言のメモリ保存」とは、多人数会話の発言 1 件（参加者・人間どちらでも）を
人間が選び、内容と kind を編集してプロジェクトのメモリとして保存する操作を指す
（[multiagent_memory.go](../internal/httpapi/multiagent_memory.go)）。

- **自動抽出を行わない**。単独 assistant の規則抽出（`MaybeStoreFromUserMessage`）と「覚えて」抽出
  （`MaybeStoreFromExplicitRequest`）は多人数会話に持ち込まない。**Why**: (1) 人間の介入発言もロールプレイになり得る。
  「I am the rightful king」は semantic の cue `i am` を通り、演出指示の「常に」は procedural として保存される。抽出器に
  虚構と事実の区別は無い。(2) 「覚えて」抽出は直近メッセージを role でしか区別せず、フォールバックで最新の assistant
  メッセージ（= 参加者のセリフ）を優先して保存する。人間の発言からだけ呼んでも参加者のセリフがメモリになる。
  ターンエンジンと `storeHumanMessage` はどちらも `MemoryService` を呼ばない。
- **保存の下書き**とは、保存ダイアログが開くときの初期値（発言本文そのまま + `inferKindFromText` で推定した kind）を指す。
  kind の推定はサーバで行い（`GET /api/messages/{messageId}/memory-draft`）、cue 表をフロントに複製しない。
- 保存（`POST /api/messages/{messageId}/memory`）は手動追加・自動抽出と同じ `MemoryRepository.CreateMemory` +
  埋め込み同期を通るので、検索・organizer の対象になる。`source` は `multi_agent`（chat kind と同じ綴り）、
  `source_chat_id` は会話の id。`locked` の既定は手動追加と同じ `true`（文言を人間が決めたので organizer に書き換えさせない）。
- **一時チャット**（`is_temporary`）の多人数会話は資料・メモリを読むが、発言のメモリ保存を受け付けない（下書き・保存とも 409）。
  画面では保存ボタンを無効にし、理由を composer の注記に出す。一時チャットの意味を「読むが書かない」に揃えるため、
  作成フォームのチェックボックスは多人数会話でも有効（TASK-17 の無効化を戻した）。
- ファシリテーター参加者による自律的なメモリ書き込みと、参加者が「これは記録に値する」と提案する仕組みは入れない
  （帰属と方針の問題に対して初期価値が小さい）。複数の発言にまたがる結論を要約して保存の下書きにする経路は別タスク。

### 4.5 進行役を挟むターン規則（`facilitator_alternating`）

2026-09-22（TASK-21）に足した 3 つ目のターン進行ルール。進行役（§2）と進行役以外の参加者が
1 発言ずつ交互に話し、進行役以外は編成の `sort_order` 順に循環する。TRPG のように、GM が毎ターン
状況を描写して次のプレイヤーへ渡す進行を、`manual` の手動指名なしで自動進行（§4.1）に乗せるためのもの。

次の話者は `round_robin` と同じく**保存済みの発言だけ**から導く（サーバー側に進行状態を持たない、§2）。
手順は上から順に:

1. 編成に進行役が居なければ、`round_robin` の導出に落とす（後述）。
2. transcript の**末尾のメッセージ**が `participant_id` を持たない（人間の介入発言、および多人数会話に
   なる前のアシスタント発言）とき、および発言が 1 件も無いとき → 進行役。
3. 末尾が進行役以外の参加者の発言 → 進行役。
4. 末尾が進行役の発言 → 進行役を除いた編成を `sort_order` 順に見て、**進行役以外で最後に発言した参加者の次**。
   その参加者が除籍済みで位置が定まらないとき、および進行役以外の発言がまだ無いときは、進行役を除いた編成の先頭。

**人間の介入発言の次は進行役**（手順 2）。**Why**: `round_robin` は `participant_id` を持つ直近メッセージ
だけを読むので介入を素通りするが、卓に投げられた言葉を受けるのは進行役の役である。進行役以外の巡回位置は
介入で狂わない — 手順 4 は進行役以外の発言だけを見るので、介入を挟んでも次のプレイヤーは変わらない。
開幕ターン（発言 0 件）も同じく進行役にするのは、場面を開くのが進行役の役だからである。

**進行役が編成に居ないときは `round_robin` に落とす**（手順 1）。規則だけ選んで進行役を指定していない場合と、
指定した参加者を除籍した場合の両方が該当する。**Why**: 規則は chat に残り続ける設定なので、除籍はいつでも
この状態を作れる。ターンをエラーにすると自動進行がその場で止まり、原因は画面の文言でしか伝わらない。
落とせば会話は進み、編成パネルは「進行役が編成にいない」ことを、直せる場所と同じ画面に出せる（§6）。
除籍時に `facilitator_participant_id` を消さないのは、指し先の消えた id と未指定がエンジンにとって同じ場合で、
消す処理を足しても増えるのは書き込みだけだからである。ただし**編成パネルからの指定は編成の参加者に限り**、
除籍済みの参加者を新たに指定することはできない（§5、400）。除籍が残した値を許容することは、
新しくそれを書けることを意味しない。

**参加者が 1 人だけ（進行役のみ）の編成**では進行役が続けて話す。多人数会話は参加者 2 人以上（§2）なので
通常は到達せず、観戦ビューはそもそも編成が 2 人未満のあいだターンを実行させない（§6）。

### 4.6 発言本文の呼びかけを重みに織り込むターン規則（2026-09-22、TASK-28、spike）

「呼ばれた人が答える」「しばらく黙っていた人に話が回る」「同じ人が続けて話さない」という会話の流れを、
既存の 3 規則を置き換えずに第 4 のターン進行ルール `weighted` として表現する設計。TASK-28 の spike で決め、
TASK-34 で実装した（導出は [turnweighted.go](../internal/service/turnweighted.go)、検出は
[addressing.go](../internal/service/addressing.go)）。決めた係数・規則と、それを支える測定をここに置く。

ここで**呼びかけ**とは、ある発言の本文が、次に話す相手として編成の参加者 1 人以上の表示名を挙げていることを指す。
`manual` で人間がリクエストに参加者を書く「指名」、および §7「将来」の**進行役による指名**（進行役がモデル出力で
次の話者を選ぶ規則）とは別物なので、別の語を与える。両者の関係は 4.6.8 で整理する。

#### 4.6.1 規則 `weighted`

ターン開始時に編成の参加者 1 人ごとに**話者の重み**（次の話者としての優先順位を表す実数）を求め、
最大の参加者が話す。重みは**係数**（個々の規則が 1 人の重みに掛ける実数）の積とする。起票時の原案にあった
「減らした分を他の参加者へ按分する」操作は積と等価ではなく（等重みの 3 人で A を ×0.2 して比例按分すると
1:7:7、積を正規化すると 1:5:5）、適用順序にも依存するので採らない。合計 1 への正規化は表示のときだけ行う。

| 係数 | 掛かる相手 | 値 |
| --- | --- | --- |
| 連続発言の抑制 | 末尾のメッセージを書いた参加者。ただし末尾が人間の介入発言なら誰にも掛からない（4.6.7） | ×0.2 |
| 直近発言の抑制 | 直近 n ターン（n = 編成の人数）のうちに発言した参加者。進行役は対象外 | ×0.85 |
| 未応答の呼びかけの加点 | 未応答の呼びかけを持つ参加者（後述） | ×1.2 |

**同点規則**（重みが最大の参加者が 2 人以上いるときに 1 人へ絞る規則）は、**沈黙が長い参加者を採り、
なお同点なら名簿順の先を採る**。一度も発言していない参加者は、発言したことのあるどの参加者よりも
沈黙が長いものとして扱う。

**重みは粗いふるいで、順序は同点規則が決めている。** 係数が 3 つとも離散値なので、重みが取る値も数点しかなく、
定常状態では 60 ターンのうち 16〜21 回（進行役の居ない 3 人編成では 59 回）最大値が並ぶ。
重みが担っているのは「直前の話者を外す」「呼びかけられた参加者を持ち上げる」「進行役を戻す」の 3 つで、
そこで絞られた候補の中で誰が先かは沈黙の長さが決めている。これは欠陥ではなく、この規則が実際に行っていることである
（4.6.3 読み取り 4）。

##### 呼びかけの窓

**呼びかけの窓**とは、呼びかけの検出結果が次の話者の決定に効き続ける範囲を指し、**直近 n 件の参加者発言**
（n = 編成の人数）と定める。**未応答の呼びかけ**とは、呼びかけの窓のうちに呼びかけられ、その呼びかけより後に
まだ発言していない状態を指す。人間の介入発言は窓を消費しない（直近発言の抑制の窓と同じ扱い。介入は誰かが
取ったターンではないので、窓の広さが人間の発言頻度に左右されるべきではない）。ただし介入が**した**呼びかけは読む
（窓を消費するかどうかと、本文に呼びかけがあるかどうかは別の話である）。

窓の**大きさは結果にほとんど影響しない**（窓 2・4・8 が全シナリオでほぼ一致、読み取り 3）。
名簿人数を採るのは、直近発言の抑制の窓と同じ値にして説明を 1 つに保つためで、測定上の理由はない。

**呼びかけの係数は、呼びかけ先以外を下げるのではなく、呼びかけ先を上げる形にする。**
起票時の原案は「呼びかけ先以外を ×0.5」だった。順位としては「呼びかけ先を ×2.0」と等価だが、
呼びかけは末尾のメッセージ 1 つからしか読めないので、`[A, B]` の A が話した瞬間に B への呼びかけが
視界から消える。窓と加点に替えると、呼びかけは他の係数と競合しながら、応答されるまで効き続ける。

##### 加点の値

**呼びかけが越えなければならないのは、重み `1.0` の参加者である。** 定常状態では編成のほとんどが
直近発言の抑制 ×0.85 を受けているが、`1.0` に居る参加者が 2 通りある — 免除された**進行役**（常時）と、
**窓を越えて沈黙した参加者**（一時的に。×0.85 を受けなくなるため）。呼びかけられた参加者の
`0.85 × 加点` がこれを越える条件が **加点 > 1/0.85 ≈ 1.176** である。

- ×1.1 はこれを下回るので呼びかけが通らない（即時追従率 11/21。加点を外した 11/21 と同値）。
- **×1.2 / ×1.3 / ×2.0 は全シナリオで完全に一致する。** 1.176 を越えた時点で飽和し、それ以上強めても
  結果が 1 発言も変わらない（読み取り 2）。
- 採用値は ×1.2 とする。飽和域の下端に近く、境界からの余裕が説明できる値であること以外に、
  この帯の中で値を選ぶ理由は測定から出てこない。

**進行役が居ない編成でも境界は無くならない。** 沈黙が窓を越えた参加者が `1.0` に上がるので、
そのときは同じ条件が効く（3 人・進行役なしで、3 発言沈黙した参加者の `1.0` が、直近に発言した
呼びかけ先の `0.85 × 1.1 = 0.935` に勝つ）。違うのは、その状態が常時ではなく呼びかけが巡回を
乱したときだけ現れることである。

##### 名簿順の維持を置かない

起票時の原案は「名簿順の次以外を ×0.95」を持っていたが、**置かない**。

- **発言順を変えていなかった。** 呼びかけの無い編成では、この係数を戻しても全指標が一致し、変わるのは
  同点の回数だけである（4 人・進行役ありで 同点 0 対 16、3 人で 0 対 59）。同点規則の「沈黙が長い側」が
  この係数と同じ参加者を指すためで、係数は同点を事前に潰していただけだった（読み取り 1）。
- **呼びかけの必要加点を上げていた。** 呼びかけられた参加者が名簿順の次でないとき、この係数を受けて
  `0.85 × 0.95 × 加点` になるので、進行役の `0.95` を越える条件が `1/(0.85 × 0.95) ≈ 1.238` に上がる。
  ×1.2 では足りず、戻すと即時追従率が 21/21 から 14/21 に落ちる（読み取り 1）。

##### 比較のために書いた対案

**`addressed_first`**: 呼びかけ先が話し、呼びかけが無ければ既存の導出（進行役が編成に居れば §4.5 の交互、
居なければ `round_robin`）に落ちる、係数を持たない優先順位付きの規則。呼びかけ先の選び方と窓の有無で
3 変種を測った — 先頭を採る形、集合から沈黙が長い側を採る形、窓のうちで未応答のものから沈黙が長い側を
採る形。不採用の理由は 4.6.4 にある。

#### 4.6.2 シミュレーションと観測量

`weighted` の係数の候補と `addressed_first` の 3 変種、既存 2 規則を
[tools/turn-score-sim](../tools/turn-score-sim/main.go) で 60 ターン回して比較した
（`go run ./tools/turn-score-sim`）。どの規則も保存済みの発言だけから話者を導く（§2）ので、
データベースもモデルも要らず、発言の列の上でそのまま回せる。

**呼びかけの発生はシナリオごとに一度だけ抽選し、全規則が同じ呼びかけを相手にする。** 話者からのオフセットとして
持つので、話者が違っても同じターンに同じ人数の呼びかけが起きる。**Why**: 抽選を使う場所で引くと、
「話者以外」を棄却抽選する回数が誰が話したかに依存し、規則ごとに呼びかけの列が分岐する。
同一シナリオの行が 17〜22 件の呼びかけを相手にしていた状態で互いに比較していた。

**変種は一度に 1 つだけ変える。** 採用案を基準に、加点の値・窓の大きさ・応答で消えるか・名簿順の係数・
同点規則・人間の介入の扱いをそれぞれ単独で振った行を持つ。

観測量の定義:

- **連続発言率**: 隣り合う 2 つの保存済みメッセージの話者が同じ参加者である組の割合。
  人間の介入を挟んだ組は、観戦者から見て続けて話してはいないので数えない。
- **最大発言シェア**: 最も多く発言した参加者の、参加者発言全体に対する割合（均等なら 1/人数）。
  誰かが会話に居座っていないかを見る。即時追従率と一巡ターン数がどちらも健全に見えていて、
  実は 1 人が 4 割を取っていることがありうる。
- **一巡ターン数**: 任意のターンから数えて、編成の全員が 1 回以上話すまでに要したターン数の最大値。
  どの起点からも全員が揃わない場合は「一巡せず」と書く。
- **進行役の間隔**: 進行役の発言と発言のあいだに入った、進行役以外の発言の数（最小〜最大）。
- **即時追従率**: 呼びかけのあった**次の**ターンで、呼びかけられた参加者のいずれかが実際に話した割合。
- **応答待ち**: 呼びかけられた参加者が実際に話すまでに要したターン数の最大値と、応答が無かった件数。
  **窓つきの形は遅れて応答することを許すので、即時追従率だけでは評価できない。**
  **呼びかけの後に参加者発言が n 件（= 窓の大きさ）揃っていない呼びかけは数えない**: 打ち切り位置に
  当たっただけで、応答されなかったのではない。この補正が無いと、加点を強めた変種のほうが未応答が多く見える
  （60 ターン目に消化中だった待ち行列が計上される）。
- **複数呼びかけ待ち**: 2 人以上を呼んだ発言についての応答待ち。
- **同点**: 60 ターンのうち、重みの最大値が 2 人以上で並んだターン数。

読み取れたこと:

1. **名簿順の維持 ×0.95 は冗長で、しかも害があった。** 呼びかけの無い編成では、戻しても全指標が一致し
   同点の回数だけが変わる（0 対 16、3 人で 0 対 59）。同点規則の「沈黙が長い側」が同じ参加者を指すためである。
   一方で呼びかけの必要加点を `1/0.85` から `1/(0.85 × 0.95)` に上げるので、戻すと ×1.2 では足りなくなり、
   即時追従率が 21/21 から 14/21 に落ちる。
2. **加点は 1.176 を越えた時点で飽和する。** ×1.2 / ×1.3 / ×2.0 は全シナリオで完全に一致し、
   ×1.1 は加点なしとほぼ同じ（11/21 対 11/21）。値の選択に幅はなく、境界の上か下かだけが効く。
3. **窓の大きさは結果に効かない。** 窓 2 / 4（名簿人数）/ 8 が全シナリオでほぼ一致する。
   窓が「ある」ことだけが効いており、大きさを選ぶ測定上の理由は無い。
4. **同点規則が実質的に順序を決めている。** 定常状態で 60 ターン中 16〜21 回（進行役なしの 3 人編成では
   59 回）重みが並ぶ。同点規則を名簿順だけにすると一巡ターン数が 8 → 12、最大シェアが 32% → 40% に悪化する。
   「しばらく黙っていた人に話が回る」性質を担っているのは係数ではなく同点規則である。
5. **応答で消える形が、残る形に優る。** 一巡 8 対 12、即時追従 21/21 対 20/21、最大シェア 32% 対 38%。
   ただし残る形でも破綻はしない: 連続発言の抑制 ×0.2 が直後の再登板を止め、直近発言の抑制 ×0.85 が
   加点 1.2 を 1.02 まで削るためである。
6. **`addressed_first` は明確に劣り、窓を与えても飢餓は直らない。** 呼びかけ 3 割で一巡ターン数 **30**
   （採用は 8）で、これは**3 変種すべてに同じに起きる**。呼びかけが常に他の圧力を先取りするので、
   呼ばれない参加者が回ってこない。窓が直すのは待ちの側だけで（複数呼びかけで応答待ち 3、窓を持たない
   2 変種は 9 と 8、後者は未応答 5/39）、一巡ターン数はどの変種でも改善しない。
7. **人間の介入発言の後に ×0.2 を課し続けると、名指しの介入が届かない**（即時追従 0/12・応答待ち 5）。
   人間の発言を現ターンの発言者とみなすと 12/12・応答待ち 1 になる（4.6.7）。
8. **進行役が居るときの振る舞いは、直近発言の抑制と進行役の免除だけから出る。** どちらを外しても
   発言順は `round_robin` と一致する（間隔 3〜3・一巡 4）。
9. **窓が効くのは、呼びかけ先が複数のときと人間の介入があるときだけである。** 窓の有無だけを変えた行
   （他の 2 係数・加点・同点規則をすべて採用案と同じにしたもの）と比べると:
   - **呼びかけ先が 1 人（進行役あり）では 1 発言も違わない。** 「介入が直前の話者を呼ぶ」シナリオも同じ。
   - **呼びかけ先が複数では効く**: 最大発言シェア 32% 対 **40%**、応答待ち 4 対 **6**。
     代償は即時追従（25/26 対 26/26）と一巡（8 対 7）。
   - **人間の介入があるときも効く**: 4 人 + 介入で即時追従 20/20 対 19/20・応答待ち 1 対 2、
     3 人・進行役なし + 介入で 15/15 対 13/15・1 対 3（どちらも上の表にある）。
   - **編成の全員を呼ぶ介入でも効く**: 最大シェア 35% 対 40%、応答待ち 4 対 5。
     このシナリオでは呼びかけがこの介入しか起きないので、窓なしの形は介入のターンに全員を等しく持ち上げ
     それ以外では誰も持ち上げない。つまり**窓なしと加点なしがここでは同一の規則になる**ので、
     下の「加点の有無で変わらない」という観察と同じ 2 行を指している。
   起票時の原案（末尾のみ・他を ×0.5・**名簿順あり**）との比較は窓と名簿順の 2 つが同時に違うので、
   窓の効果はこの行からは読めない。

#### 4.6.4 決めたこと

**`weighted` を採る**（2026-09-22、ユーザー判断）。係数は 4.6.1 の表の 3 つ。

- **呼びかけは窓つきの加点で表す**（窓 = 編成の人数、×1.2、応答で消える）。起票時の原案「末尾のメッセージの
  呼びかけ先以外を ×0.5」から替えた。**Why**: 原案は呼びかけを末尾のメッセージ 1 つからしか読まないので、
  `[A, B]` の A が話した瞬間に B への呼びかけが消える。窓にすると応答されるまで効き続ける（読み取り 9）。
- **名簿順の維持 ×0.95 は置かない**（読み取り 1）。発言順を変えず、呼びかけの必要加点だけを上げていた。
- **加点は ×1.2**（読み取り 2）。境界 `1/0.85 ≈ 1.176` を越えていればよく、それ以上強めても結果は変わらない。
- **加点は応答で消える**（読み取り 5）。
- **同点規則は沈黙が長い側 → 名簿順**（読み取り 4）。これがこの規則の中核で、係数の側ではない。
- **人間の介入発言の後は、人間の発言を現ターンの発言者とみなす**（4.6.7）。進行役を強制する上書きは入れない。
- **呼びかけ先は複数を保持し、編成の全員への一致も捨てない**（4.6.5）。

**`addressed_first` を採らない理由**は読み取り 6 にある。呼びかけを最優先の規則に置くと、呼ばれない参加者が
飢える（一巡ターン数 30、採用は 8）。窓を与えても採用に届かない。呼びかけを 3 つの係数の 1 つとして扱い、
残りの順序を同点規則に委ねる形が、呼びかけへの追従と巡回の両方を保つ。

**窓を採る根拠は読み取り 9 にある。** 窓の有無だけを変えて測ると、呼びかけ先が 1 人のあいだは 1 発言も
違わず、効くのは呼びかけ先が複数のとき（最大発言シェア 32% 対 40%、応答待ち 4 対 6）と、
人間の介入があるとき（即時追従 20/20 対 19/20、応答待ち 1 対 2）である。「A さんと B さん、どう思う？」と
人間の介入はどちらも普通に起きるので、この 2 つで効くことを根拠として採る。
**係数が 3 つになったのは名簿順の係数を外したためで、窓とは別の変更である**（窓を持たない形も係数は 3 つになる）。

**採らなかった形**: 呼びかけ追従を、ターン進行ルールとは別の chat 単位の真偽値設定にして既存 3 規則すべてに
効かせる案。呼びかけを有効にした `round_robin` は、名簿順を外れることがある以上もはや `round_robin` ではなく、
「既存規則を置き換えない」という前提に反する。`turn_rule` が「次に誰が話すか」を決める唯一の場所である性質も崩れる。

既存の `round_robin` / `manual` / `facilitator_alternating` の振る舞いは一切変えない。

**この節が過去に書いていて取り消した主張**（いずれも測定の誤りによるもの。経緯は TASK-28 の実装ノート）:
「順位規則は呼びかけ先の一方を捨てるしかない」「呼びかけはスイッチとして切り替わる」
「×1.3 以上は未応答を作るので ×1.2 だけが良い」「加点の下限は直近発言の抑制が打ち消すことから来る」。

#### 4.6.5 呼びかけの検出方式と保存形式

**検出結果は発言の保存時に確定し、その発言に紐づく参加者 id の集合 `addressed_participant_ids`
（0 個 = 呼びかけ無し）として保存する。** 後から本文を読み直す形にすると、表示名の変更や除籍で答えが変わり、
再起動の前後で次の話者が変わりうる（§2）。**呼びかけの窓（4.6.1）があるので、この保存は末尾の 1 件だけでなく
窓のうちの全件が読み返される。** 本文を読み直す形だと、窓のあいだ何度も再解釈することになり、
そのどこかで答えが変われば次の話者が変わる。判定のための追加の LLM 呼び出しは行わない
（§8.1 が履歴要約を見送ったのと同じ理由: 小型モデルでは 1 ターンの遅延が倍になる）。

検出は 2 段で行う:

- **(a) 末尾の指示子**: 役割リマインド（§4.3）に「次に話してほしい相手がいるときだけ、発言の最後の行に
  `[次: 表示名]` と書く（複数なら読点で区切る）」を足し、保存前にその 1 行を剥がして id に解決する。
  §4.3 が記録したとおり小型モデルは与えられた書式を模倣しやすいので、この形は当たりやすい。
  剥がし損ねへの防御として、剥がすのは**末尾の 1 行だけ**とし、編成に一致しない表示名はその 1 件だけ捨てる
  （行ごと捨てない）。一致が 0 件なら呼びかけ無しとしたうえで指示子は剥がす（本文に制御用の記法を残さない）。
- **(b) 名前の照合（(a) が空振りしたときだけ）**: 発言の最終文に現れた編成の表示名のうち、自分自身を除いた
  ものすべてを呼びかけ先とする。(a) と違い上限を置かないのは、呼びかけ先が複数のときこそ窓つきの加点が
  効くからである（読み取り 9）。ただし**最終文に限り、表示名は 2 文字以上**とする。
  SillyTavern は単語境界（`\b\w+\b`）で照合するが、この方式は日本語の表示名から単語を 1 つも取り出せず
  検出が常に空振りする（調査資料 [_sandbox/sillytavern-natural-order.md](../_sandbox/sillytavern-natural-order.md) §3-2）。
  そのため当アプリは部分文字列一致にせざるを得ず、短い表示名の誤検出（「リン」が「リンゴ」に一致する）が起きる。
  最終文への限定と 2 文字以上の条件がその抑えである。**編成の全員が一致しても捨てない。**
  起票時は「全員が ×0.5 を免れると呼びかけが無いのと同じ重みの並びになるので、検出しても何も足さない」と
  して捨てる扱いにしていたが、加点の形（4.6.1）ではこれが成り立たない: 応答した参加者は加点を失い、
  未応答の参加者は保つので、時間が経つにつれ差が付く。「みなさん、どうですか」に対して、まだ答えていない
  参加者だけが加点を保ち続けるので、編成が一巡するまで加点が順番を押す。捨てるとこの機構が働かない。
測定では最大発言シェアが 35% 対 40%・応答待ち 4 対 5 動く（読み取り 9 の 4 番目）。
  呼びかけ先が複数のときの差（32% 対 40%）と同じ程度なので、小さいとは言えない。

**人間の介入発言にも検出をかける**（(b) のみ。人間は指示子を書かない）。測定の「介入が直前の話者を呼ぶ」行が
示すとおり、かけなければ「A さん、もう少し詳しく」と書いても A は答えられない。介入は `POST /messages` で
保存されるので（§4.4）、検出はターンの書き込みと介入の書き込みの両方に置く。

**自分自身への呼びかけは捨てる。** そのうえで「呼びかけ先が直前の発言者」という状態は残る
（人間が直前の話者に「もう少し」と促した場合）。その participant が続けて話すのが正しいので、
4.6.7 の扱いがこれを通す。

**実装で決めた細部**（2026-09-22、TASK-34）:

- **検出と保存は規則によらず、多人数会話のすべての発言で行う。** 指示子を書くよう求めるのは `weighted` のときだけだが
  （§4.3）、読む側の窓は保存済みの呼びかけを読むので、途中で規則を `weighted` に切り替えた会話でも直前の呼びかけが効く。
  既存 3 規則は呼びかけを読まないので、保存しても話者の選択は変わらない（テストで確認）。
  他の規則の下でモデルが指示子を書いた場合も剥がす（本文に制御用の記法を残さない、は規則によらない）。
- 指示子の書式は `[次: 表示名]` を基本に、全角の `［` `］` `：` も受ける。区切りは読点のほか `,` `，` も受ける。
  発言の末尾にあれば、改行なしで最終文に続けて書かれたものも剥がす。末尾以外にある同じ形の文字列は本文として残す。
  表示名との一致は前後の空白を除いた完全一致（英字は大文字小文字を区別しない）。
- **参加者を指す名前は、表示名そのものと、表示名の末尾の括弧書きを除いた部分の 2 つ**とする（(a)・(b) の両方）。
  **Why**: 同梱の `trpg-table` はプレイヤーを「レン (斥候)」「ミラ (神官戦士)」と名付けているが、gemma-4-e4b の GM は
  実機で `[次: レン, ミラ]` と書いた。完全一致だけでは呼びかけがすべて捨てられ、検証シナリオが成り立たない。
  括弧書き（半角・全角）は役割の注記で、呼ぶ側が書くのは前の名前だけである。2 文字以上の条件は括弧書きを除いた側にも掛ける。
- **編成の 2 人以上が同じ名前を持つとき、その名前は誰も呼ばない**（表示名そのものでも、括弧書きを除いた名前でも）。
  同梱の交渉プリセットは「買い手 (情シス担当)」「買い手 (部長)」を持ち、どちらも「買い手」になる。一致させると両方を呼ぶか、
  先に並んだ方だけを呼ぶことになり、名指しした相手と違う参加者が話す。2 人は表示名そのものでなら呼べる。
- 最終文とは、末尾の文区切り（`。` `．` `！` `!` `？` `?` 改行、および空白か末尾が続く `.`）と閉じ括弧・引用符を落としたうえで、
  最後の文区切りより後ろの部分を指す。「彼は言った。「アリス、来て。」」の最終文は「「アリス、来て」」である。
- 呼びかけ先は編成（除籍済みを除く）からだけ選ぶ。人間の介入発言の検出も同じ。
- **指示子の行しか無い発言はターンの失敗にする**（`ErrUtteranceOnlyDirective`）。剥がすと本文が空になり、
  空の発言を保存しない §4.3 の扱いと揃える。
- 生成中のストリームは剥がす前の本文を流すので、観戦ビューでは生成中だけ指示子が見え、`done` で保存済みの本文に置き換わる。

#### 4.6.6 次の話者と重みの内訳をどう画面に出すか

TASK-33 まではフロントの `turnOrder.ts` の `predictNextSpeaker` がエンジンと同じ導出を複製していた（TASK-33 で削除）。
`weighted` を足すと複製は 3 係数と同点規則の分まで増え、検出結果（`addressed_participant_ids`）をフロントへ
流す必要も出る。算術を二重に持つべきではない。

**決定: ターンの SSE に、生成開始の直前で `speaker` イベントを 1 つ足す。** 内容は選ばれた話者と**重みの内訳**
（参加者ごとの重みと、その重みに掛かった係数の一覧）。フロントの導出は消す。重みの内訳を同じイベントに
載せるのは、それが話者を決めた計算そのもので、話者と同じ瞬間に確定しているからである。
画面は「なぜこの人が話しているか」を、係数の名前と値の並びとして観戦ビューに出す（重みは正規化せず、積のまま出す）。TASK-33 で決めた形は、
生成中の発言の吹き出しに畳んだ「この話者になった理由」を置き、開くと参加者ごとに `重み = 係数名 ×値 · …` を 1 行ずつ
並べるもの。内訳が空の規則（`round_robin` / `manual` / `facilitator_alternating`）では何も出さない。
内訳は発言と一緒には保存しないので、生成が終わると消える。

イベントの形は `{ participant, modelName, weights }`。`participant` は参加者の行そのもの（走行中に追加された参加者でも
フロントが名前を引ける）、`modelName` は継承を解決した後の実際のモデル名、`weights` は
`[{ participantId, displayName, weight, factors: [{ name, value }] }]` で、内訳を持たない規則では空配列（`null` にはしない）。
`weighted` は編成の全員を 1 行ずつ載せ、`factors` にはその参加者に掛かった係数だけを並べる（掛からなければ空で、重みは 1）。
係数名は `consecutive`（連続発言の抑制）・`recent`（直近発言の抑制）・`call`（未応答の呼びかけの加点）で、
画面の言語に合わせた表示名への置き換えはフロントが行う（知らない名前はそのまま出す）。
`displayName` は TASK-34 で足した。フロントがまだ読んでいない参加者でも内訳に名前が出る。

イベントを足す位置は**ターン前の確認をすべて通した後**でなければならない。`handleRunTurnStream`
（[multiagent.go](../internal/httpapi/multiagent.go)）は TASK-33 以前は最初の delta が来るまで SSE ライタを開かず（現在は `speaker` で開く）、
ストリームが開く前の失敗だけが HTTP ステータスとして返るためである。`RunTurn` は話者選択 → 接続先解決 →
`endpointAccepts` の順に進むので、`endpointAccepts` の直後に置けば、そこまでに決まるステータスはすべて残る:
ターンの重複 409、chat 不在・参加者不在 404、規則と指名の不整合・除籍済みの指名 400、エンドポイント不通 502。

**ただし「ステータスが 1 つも変わらない」わけではない。** `endpointAccepts` より後の失敗
（参加者一覧の読み出し、生成そのもの、発言の保存）は、現在は delta が 1 つも届いていなければ
`turnErrorResponse` の既定分岐で **HTTP 500** になり、delta が届いていればストリーム内の `error` イベントになる。
`speaker` を先に出すとストリームは常に開いているので、**この 500 は一律にストリーム内の `error` に変わる**。
これは受け入れる変更として扱う。**Why**: 同じ失敗が「delta が 1 つでも届いたか」で 500 とストリーム内 error に
分かれる現在の挙動のほうが不揃いで、フロントは既にストリーム内 `error` を扱える（§6 の観戦ビュー）。
TASK-33 はこの変更を明示的に検証項目に持つ。

**採らなかった形**: (1) `GET /api/chats/{chatId}/next-speaker` の事前問い合わせ — ターンごとに 1 往復増え、
しかも問い合わせと実行のあいだに介入が入ると答えが古くなる。(2) `done` フレームに次ターンの話者を載せる —
次のターンの前提（介入・編成の変更・規則の変更）はそのあいだに変わりうるので、載せた時点で正しいとは限らない。

#### 4.6.7 人間の介入発言の後に誰が話すか

**人間の発言を「現ターンの発言者」とみなし、連続発言の抑制 ×0.2 を参加者の誰にも課さない。**
名指しの無い介入では、これにより進行役が（直近発言の抑制の対象外である分だけ）応じやすくなる。

**Why**: ×0.2 を直近の参加者発言者に課し続けると、人間が直前の話者を名指しで呼んでも届かない。
呼びかけ先は加点を受けても `0.2 × 0.85 × 1.2 = 0.204` にしかならず、他の誰かの 0.85 以上に負ける。
測定では即時追従率 **0/12**・応答待ち 5 ターン。人間の発言を現ターンの発言者とみなすと
`0.85 × 1.2 = 1.02` になり、**12/12**・応答待ち 1 ターンに変わる。
意味の上でも、人間が間に挟まったのだから、その participant は続けて話してはいない。

TASK-21 が `facilitator_alternating` について決めた「人間の介入発言の次は進行役」（§4.5 手順 2）とは
揃わないが、`weighted` は §4.5 とは別の規則として並置されるので、既存の規則の振る舞いは変わらない。

**進行役を強制する上書きは、2 つの形のどちらも入れない。**

- **名指しの有無によらず強制する形**: 名指しの介入で即時追従率が 11/12 に落ちる（採用案は 12/12）。
  人間が名指しで呼んだ相手より進行役を先に立てるので、これは害である。
- **名指しの無い介入のときだけ強制する形**: 測定した 2 シナリオで、一巡ターン数・即時追従率・応答待ちが
  採用案と一致する（一巡 9 / 6、即時追従 20/20 / 12/12、応答待ち 1 / 1）。同点の回数は比較できない
  （上書きは重みを計算せずに話者を返すので、そのターンは同点として数えられない）。
  進行役の免除によって進行役はすでに応じやすく、上書きはその傾向を確定に変えるだけで、
  この 2 シナリオでは観測した指標を動かさなかった。
  得るものが無いのに、規則が「重みで決める」一点では済まなくなるので入れない。
  介入の直後に進行役が応じることを確定させたいなら、`facilitator_alternating` を選べば規則として得られる。

#### 4.6.8 §0・§7 の非ゴールとの関係

§0 と §7 が将来へ置いている**進行役による指名**は、「**進行役が**モデル出力で次の話者を選ぶ」ことを指す。
`weighted` はモデルの出力を読む点で同種だが、読む対象を進行役に限らず**どの参加者の発言でも**、
さらに人間の介入発言でも同じに扱い、しかも読んだ結果は次の話者を決める 3 つの係数のうちの 1 つにすぎない。
進行役という役割に依存しないので、進行役を持たない編成でも効く。
§0 の非ゴールの文言は TASK-34 でこの整理に沿って更新した。決定的に進行役を挟む `facilitator_alternating`（§4.5）は
モデル出力を一切読まないので、この整理の影響を受けない。

#### 4.6.10 SillyTavern の natural order との比較、および `talkativeness` を入れるか

先行実装として SillyTavern のグループチャット natural order を調べてある
（[_sandbox/sillytavern-natural-order.md](../_sandbox/sillytavern-natural-order.md)）。
そのまま移せる設計ではないが、当アプリに無いものが 1 つあるので、入れるかを判断した記録を置く。

| 論点 | SillyTavern natural order | `weighted` |
| --- | --- | --- |
| 1 リクエストで話す人数 | 0〜全員（応答者リストに入った全員が順に話す） | 常に 1 人（§4.1） |
| 決定性 | 乱数（talkativeness の抽選と名簿のシャッフル） | 決定的（保存済み発言だけから導く、§2） |
| 呼びかけの検出 | 単語境界 `\b\w+\b` の完全一致。**日本語の表示名は検出できない** | 最終文の部分文字列一致、2 文字以上、自分自身を除く（4.6.5） |
| 呼びかけの有効範囲 | その生成 1 回のみ | 呼びかけの窓のうち、未応答のあいだ（4.6.1） |
| 呼びかけの効き方 | 応答者リストに入れる（他の参加者も抽選で入りうる） | ×1.2 の加点（他の 2 係数と競合する） |
| 同じ人の連続 | Allow self responses で切り替え（直前の話者を除外） | ×0.2 |
| 沈黙の考慮 | **無い**（抽選は履歴を見ない） | ×0.85 と同点規則の 2 つ |
| 参加者ごとの発言頻度 | `talkativeness`（0〜1 の確率。既定 0.5） | **無い**。進行役が ×0.85 を免除されることだけが特殊ケース |
| 誰も選ばれないとき | `talkativeness > 0` の中からランダムに 1 人 | 起きない（重みの最大値は必ず 1 人以上いる） |

**交換関係になっている。** SillyTavern は多様性（乱数と個体差）を持つ代わりに公平性を持たず、
`weighted` は公平性（沈黙の考慮）を持つ代わりに個体差を持たない。

**`talkativeness` は入れない。** 当アプリは決定的なので、これを実装できる形は「参加者ごとの定数係数を
重みの積に足す」しかない。SillyTavern の確率とは故障の仕方が違う: 抽選なら 0.2 でも 5 回に 1 回は当たるが、
定数係数では**構造的に勝てない参加者が生まれる**。4 人（GM + A/B/C）・呼びかけ 3 割・60 ターン、
C だけ係数を下げ、**基準行を含む全行を同じ seed で回した**（基準行だけ別シナリオや別 seed から引くと、
差のどこまでが係数によるものか言えない）:

| C の係数 | 最大シェア | 一巡ターン数 | 即時追従 | 応答待ち |
| --- | --- | --- | --- | --- |
| 1.0（係数なし = 採用案） | 33% | 7 | 11/11 | 1（10 件・未応答 0） |
| 0.8 | 45% | **39** | 10/11 | 2（10 件・未応答 0） |
| 0.5 | 47% | **一巡せず** | 7/11 | 1（**未応答 3**/10） |
| 0.2 | 47% | **一巡せず** | 7/11 | 1（**未応答 3**/10） |

**0.8 の時点で一巡ターン数が 7 から 39 に跳ね、0.5 では一巡に加わらなくなる。**
「少し控えめ」と設定したつもりの値でその参加者が会話から落ちる。「控えめ」を設定した利用者が得るのは
「無言」であり、同じ名前の設定が先行実装と違う意味になる。

**入れるなら、沈黙を連続量にする変更と抱き合わせでなければならない。** ×0.85 を
`×(1 + 0.15 × 沈黙ターン数)` のような増える項に置き換えれば、長く黙った参加者はいずれ定数係数の不利を
上回れる。これは係数 1 つの追加ではなく規則の形の変更なので、必要になった時点で別に設計する。

**ただし、進行役の免除は `talkativeness` の一種として書けることが測定で分かった。** 免除を外して
進行役に係数 `1/0.85 ≈ 1.176` を与えると、4 人（GM + 3）・呼びかけなしの編成で採用案と全指標が一致する
（進行役の間隔 1〜3、一巡ターン数 5、最大発言シェア 40%）。等価な係数がちょうど `1/0.85` になるのは、
免除が与えているものが「×0.85 を受けないこと」に尽きるからである。
**この一致は測定したこの 1 シナリオについての主張である。** 係数を外すこと（1.0 にすること）と 1.176 を
与えることは別の関数で、進行役が窓を越えて沈黙した場合など、免除では同点になり係数では勝ち切る状態では
振る舞いが分かれる。測定したシナリオは呼びかけも介入も無いのでその状態に入らない。測定したシナリオの範囲では、`weighted` は参加者ごとの発言頻度を
1 つ、コードに焼き込んで持っているとみなせる。将来 `talkativeness` を入れるなら、免除をデータ側へ移して特殊ケースを
無くす形が考えられる（測定したシナリオでは結果が変わらないが、上に書いた分かれ方があるので
「何も変わらない」とは言えない）。TASK-34 の範囲外とする。

**応答者リストの方式（1 リクエストで複数人が話す）も移さない。** 1 リクエスト = 1 ターンは §4.1 の
決定で、観戦者がターンごとに見て介入できることがその目的である。リストを待ち行列として保存すれば
移せるが、それはサーバー側に進行状態を持つことになり §2 に反する。呼びかけの窓は、同じ「複数人に
順に話させる」効果を進行状態なしで得るための形である（`[A, B]` の両方が未応答のあいだ加点を持つ）。

### 4.7 刻々と変わる状態の置き場（2026-09-22、TASK-22、spike、**未実装**）

TRPG では HP・所持品・現在地・残り時間がターンごとに変わる。これは耐久性のある事実ではないのでメモリには入れず
（§4.4、TASK-19）、静的でもないのでドキュメントにも向かない。spike 時点の受け皿は場面設定を人手で書き換えることだけで、
履歴は直近 30 発言で切られるので古い状態変化は消える（§4.3）。この節はその置き場を決める。実装は TASK-35・TASK-36 で、
本文のうちこの節だけは実装より先に書いた設計である。

#### 4.7.1 用語

- **状態項目**とは、持ち主・項目名・値の組 1 つを指す。例:（レン, HP, 7/10）。
- **状態シート**とは、1 つの持ち主の状態項目を「項目名: 値」の行で並べたテキストを指す。持ち主は 2 種類ある:
  - **共通の状態**: 持ち主が chat のもの（場所・時刻・残り時間）。`chats.state_sheet`。
  - **参加者の状態**: 持ち主が参加者 1 人のもの（HP・所持品・状態異常）。`participants.state_sheet`。
- **【現在の状態】節**とは、話者の system prompt に入れる、共通の状態と全参加者の状態をまとめた節を指す。
- **アクションの効果**とは、アクションの結果として、アプリが状態項目に当てる操作を指す。
  アクションは TASK-23 で効果コマンド（§4.8.4）として定めた。

「キャラクターシート」は参加者側だけを指し共通の状態を含まないので、この節では使わない。

#### 4.7.2 測定

更新の主体と prompt 内の位置の 2 点は、小型モデルでの挙動が論点なので実測した（2026-09-22）。
同梱 `trpg-table` の GM の system prompt を §4.3 の組み立てどおりに再現し（場面設定 + 【現在の状態】節 + 役割 + 参加者一覧 + リマインド）、
GM の過去発言を `assistant`、プレイヤーの発言を「表示名: 本文」の `user` に写像した履歴を渡した。temperature 0.25（既定値）、
各条件 5 回。計測スクリプトはリポジトリに置いていない（使い捨て）。条件は以下で再現できる。

状態シートの初期値は「場所 / 時刻 / レン HP 7/10 / レン 所持品（たいまつ 2 本）/ ミラ HP 14/14 / ミラ 所持品（包帯 3 巻）」の 6 行。

- **更新ブロック**: リマインドに「状態が変わったときだけ、発言の最後に `[状態]` の行を置き、その下に変わった項目を書く」を足し、
  直前のプレイヤー発言を 3 通りにした。包帯でレンを手当てする（包帯と HP が変わる）、第二坑道の分かれ道へ進む（場所が変わる）、
  台詞だけ（何も変わらない）。書き方は差分（変わった項目だけ）と全書き直しの 2 通り。
- **履歴との食い違い**: シートは「たいまつ 0 本」、履歴の GM 発言は「たいまつは残り 2 本」、直前のレンの発言は「たいまつを灯す」。
  GM がシートに従って点火を認めないかを、【現在の状態】節の位置 3 通り（場面設定の前 / 場面設定の直後 / リマインドの直前）で見た。

| 測定 | gemma-4-e4b | gpt-oss-20b |
| --- | --- | --- |
| 変わる場面（包帯・移動）で更新ブロックを書いた（差分） | 0/10 | 2/10（項目名を `Mirra` / `Ren` と英語で書き、表記どおりは 0） |
| 同（全書き直し） | 未測定 | 1/10 |
| 場所の移動を書いた | 0/5 | 0/10 |
| 何も変わらない場面で余計なブロックを書いた | 1/5（「なし」だけのブロック） | 0/10 |
| 履歴と食い違うとき、シートに従った（位置 3 通りの合計） | 未測定 | 0/15 |

読み取り:

1. **モデルに状態を書かせる経路は、どちらの書き方でも使えない。** 書く率が低いうえ、書いても項目名が表記から外れ、
   アプリが行を特定できない。
2. **シートの位置で結果は変わらない。** どの位置でも GM は 15 回すべて点火を認め、6 回は履歴の「2 本」から数えて
   「1 本」に更新した。「履歴と食い違うときはこちらを正とする」の前置きも効いていない。シートは参考情報として読まれるが、
   直前の宣言と履歴には勝たない。
3. したがって、「持っていない物は使えない」のような**前提条件の判定は prompt では担保できない**。アプリの側で判定するなら
   アクションの判定（TASK-23）の責務になる。

gemma-4-e4b は途中まで（差分の 15 回）でローカルの測定を打ち切り、以降は LAN 上の gpt-oss-20b で測った。

#### 4.7.3 決めたこと（2026-09-22、ユーザー判断）

**1. 状態の表現 — 共通の状態と参加者の状態の 2 種の状態シート。** 案は 3 つあった。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 場面設定を「固定の設定」と「現在の状態」に分ける | 不採用 | 持ち主が chat しか無く、参加者ごとの HP・所持品を行の書き分けでしか表せない。アクションの効果（下記 2）が参加者を指して更新する先が無い |
| chat に状態シートを 1 つ足す | 共通の状態として採用 | 場所・時刻のように誰のものでもない項目の置き場 |
| 参加者ごとのシート | 参加者の状態として採用 | TASK-23 のアクションは参加者が起こし、その効果は多くが本人の項目（HP・所持品）に当たる |

状態シートは JSON ではなく行のテキストにする。アプリが読むのは「持ち主 + 項目名」で特定した 1 行の値だけで、
ゲームごとのスキーマを持つ理由が無い。人間はテキスト欄でそのまま編集できる。
§7「将来」が書いていた「chat 単位の JSON 状態」はこの決定で置き換えた。

**2. 更新の主体 — 人間の編集と、アクションの効果。モデルは状態を書かない。**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 人間だけが編集する | 採用（経路の 1 つ） | 確実で、モデル呼び出しを増やさない |
| 進行役の発言から抽出して更新する | 不採用 | 毎ターン LLM 呼び出しが 1 回増え、ローカル小型モデルで 1 ターンの遅延が倍になる（§8.1 で要約を退けた理由と同じ）。抽出の精度も 4.7.2 の書き込み率を超える根拠が無い |
| 発言の末尾に構造化した更新ブロックを書かせる | 不採用 | 4.7.2 の読み取り 1 |
| アクションの効果をアプリが適用する | 採用（経路の 1 つ） | 出目と判定をアプリが持つなら（TASK-23）、その結果の状態変化も同じ場所で決まり、モデルの書き込み率に依存しない |

アクションの効果の基本操作は 2 つにする。`set` は持ち主 + 項目名で行を特定して値を置き換える（行が無ければ末尾に足す）。
`add` は値の先頭の整数に加減する（`HP: 7/10` に −3 で `4/10`）。先頭が整数でない値には `add` を適用しない。
どのアクションがどの効果を生むか、前提条件（所持品が無い等）をどこで判定するかは TASK-23 で決めた（§4.8.4）。

**3. prompt 内の位置 — 場面設定の直後、役割プロンプトの前。**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| プロジェクト資料と場面設定の間 | 不採用 | 固定の世界（場面設定）より先に現在の状態を読ませることになり、順序が逆 |
| 場面設定の直後・役割の前 | 採用 | 固定の世界 → 現在の状態 → 自分が誰か、の順に読める。§4.3 の「役割がリマインドの直前で最後に読まれる」を保つ |
| リマインドの直前 | 不採用 | 役割をリマインドから遠ざける。4.7.2 では位置による差が出ておらず、§4.3 の順序を崩す見返りが無い |

【現在の状態】節は 1 つにまとめ、共通の状態を先に、続いて参加者の状態を編成順に表示名の見出し付きで並べる。
すべての状態シートが空なら節ごと出さない（既存の会話の prompt は変わらない）。
**全参加者に全員分を渡し、`receives_project_material` には依らない**（ユーザー判断）。GM は全員分が要り、
卓の上のシートは公開情報として扱う。伏せたい状態（敵の残り HP など）はプロジェクト資料（§4.4、GM にだけ渡す）に置く。
§4.4 がメモリの `shared_with_all` の既定で述べたとおり、多人数会話には他の参加者に見えない発言が無いので、
会話の中で変わった状態を一部の参加者から伏せても隠せるものが少ない。

**4. 上限 — 共通の状態 400 字、参加者の状態 1 人 200 字。** 参加者 3 名の卓で 1,000 字で、プロジェクト資料（2,000 字、§4.4）の半分、
履歴（約 6,000 字）の 1/6 に収まる。4.7.2 のシートは 6 行で約 110 字なので、1 人あたり HP・MP・所持品・状態異常を並べても 200 字に届く。
上限は**保存時に検査**し（人間の編集もアクションの効果も）、prompt 側では切り詰めない。画面に見えている内容と
モデルが読む内容を一致させるためである。効果の適用で上限を超えるときは、その効果を適用しない。

#### 4.7.4 起票した実装タスク

- **TASK-35**: 状態シートの列（migration 16）・上限の検査・API・編成パネルでの編集（会話中も可）・【現在の状態】節の注入・
  markdown エクスポート・プリセットの `stateSheet`（同梱 `trpg-table` に初期値）。
- **TASK-36**: アクションの効果（`set` / `add`）の適用と、どの発言による効果かの表示。TASK-35 と TASK-23 に依存する。
  効果を生むアクションは §4.8.4 で効果コマンドとして定めた。

### 4.8 ダイスと判定（2026-09-22、TASK-23、spike、**未実装**）

TRPG の成否はダイスの出目で決まるが、モデルに「d20 を振れ」と言うと、物語の都合に合う値を返しがちで公正にならない。
spike 時点では人間が介入発言に出目を書くことはできるが、アプリはそれを読まないので、判定の記録も状態項目への効果も残らない。
この節は、出目をアプリが出す経路・履歴上の表現・画面・アプリが持つ判定の範囲、および状態項目への効果を生むアクションを決める。
§4.7 と同じく、実装より先に書いた設計である。

#### 4.8.1 用語

- **スラッシュコマンド**とは、発言の末尾に置く `/` で始まる 1 行で、アプリが保存時に検出して実行する指示を指す
  （例: `/roll 1d20+3 目標12 岩棚を渡る`）。人間の介入発言にも参加者の発言にも書ける。
- **出目**とは、アプリがサーバー側の乱数で決めたダイスの目と、修正値を足した合計を指す。
- **判定**とは、出目の合計を目標値と比べて成功 / 失敗を付けることを指す。
- **判定の記録**とは、スラッシュコマンドを書いた発言に紐づけて保存する、コマンド本文・出目・目標値・成否の組を指す。
- **既定の目標値**とは、目標を省いた `/roll` の合計と比べる chat 単位の整数を指す（0 = 比べない）。
- **効果コマンド**とは、状態項目（§4.7.1）を変えるスラッシュコマンド（`/add`・`/use`・`/set`）を指す。§4.7 の「アクションの効果」を生むのはこれである。

#### 4.8.2 測定

論点のうち「モデルがコマンドを書くか」と「GM がアプリの出目に従うか」は小型モデルの挙動なので実測した（2026-09-22）。
同梱 `trpg-table` の system prompt を §4.3 どおりに再現し、場面設定の「ダイスは使いません」の行を次の規則に差し替えた:
結果が不確かな行動を宣言したプレイヤーは最後の行に `/roll 1d20+修正 行動` を書く（得意 +3、苦手 −2、他 +0。結果は書かない）、
出目はアプリが振り【ダイス】の行で示す、合計 12 以上で成功。temperature 0.7（ターンエンジンの値）、各条件 5 回。
計測スクリプトは使い捨てで、リポジトリに置いていない。

- **A**: GM が崩れかけた岩棚と奥の物音を描写した直後のレンの発言。**A0**: 同じ場面で、直前がミラの問いかけ（台詞）のときのレンの発言。
- **B**: レンの「岩棚を横歩きで渡る」宣言とコマンドの後に【ダイス】行を置き、それに答える GM の発言。
  B1 = 合計 7 だけを示す、B2 = 合計 7 に「目標 12、失敗」を付ける、B3 = 合計 19 に「目標 12、成功」を付ける。
  B は初回に角括弧の書式（`[判定: 岩棚を渡る 1d20+3]`）で測った。GM が読む【ダイス】行は書式によらず同じである。

| 測定 | gpt-oss-20b | gemma-4-e4b |
| --- | --- | --- |
| A・A0 でコマンドを書いた（スラッシュ形式） | 10/10 | 3/10 |
| 同（角括弧形式、参考） | 10/10 | 1/10 |
| うち独立した行にせず、本文の末尾に続けて書いた（スラッシュ形式） | 7/10 | 1/3 |
| うち行動の要約が無い（スラッシュ形式） | 3/10 | 0/3 |
| コマンドの前に結果を先取りして書いた（角括弧形式） | 1/10 | 0/1 |
| B1: 合計 7 だけで、GM が「渡りきった」と描写した | 1/5 | 2/5 |
| B2: 合計 7 +「失敗」で、GM が「渡りきった」と描写した | 0/5 | 1/5 |
| B3: 合計 19 +「成功」で、GM が渡りきったと描写した | 5/5 | 5/5 |

読み取り:

1. **モデルがコマンドを書くかはモデル次第である。** gpt-oss-20b は毎回書き、gemma-4-e4b は 3 割に留まる。
   §4.7.2 の更新ブロック（状態が変わる場面の 2/10 以下）より書かれるのは、状態を追跡させるのではなく、
   宣言する行動そのものに 1 行添えるだけだからと読める。書かないモデルでも卓を回せるよう、人間が同じコマンドを書ける経路が要る。
2. **書式の揺れは検出側で吸収する。** gpt-oss-20b では本文に続けて書かれたコマンドが 7 割あり、§4.6.5 の指示子と同じく「最終行の末尾」まで受ける必要がある。
3. **GM は出目に大筋で従うが、合計だけでは足りない。** 合計 7 だけを渡すと 10 回中 3 回が失敗を成功として描写し、
   アプリが「失敗」を付けると 1 回に減る。成否の比較はアプリが持つ価値がある。
4. 修正値の選び方は緩い（gpt-oss-20b は、レンの得意な足跡・空気の流れを読む行動でも、10 回中 9 回 +0 と書いた）。修正値の正しさはアプリでは担保しない。
   気になる卓では、場面設定・役割プロンプトに行動ごとの修正値を書く。

#### 4.8.3 決めたこと（2026-09-22、ユーザー判断）

**1. 出目の出どころ — アプリが乱数で出す。きっかけはスラッシュコマンドで、人間とモデルが同じ書式で書く。**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 人間が介入発言に出目を書く（spike 時点の姿） | 不採用 | 公正さが人間任せで、アプリは出目を読まないので判定の記録も効果も残らない |
| 介入欄の隣の「ダイスを振る」ボタン | 不採用 | 自動進行中は人間が止めないと判定が挟まらない。人間が書くコマンドと同じことを別の入口で行うだけになる |
| 発言の角括弧の指示子（`[判定: …]`）を検出する | 不採用 | 書かれる率はスラッシュ形式と同程度以下（読み取り 1）で、人間が入力欄で書く書式として馴染まない |
| スラッシュコマンドを人間の介入発言・参加者の発言の両方で検出する | 採用 | 1 つの書式で両方の経路を賄う。書けるモデルでは自動進行のまま判定が挟まり、書けないモデルでは人間が同じ 1 行を送る |

乱数は Go の `math/rand/v2` でよい。守りたい公正さは「値を物語の都合で選べない」ことで、暗号論的な予測不能性ではない。
シードの保存や再現は行わない。

**2. 履歴上の表現 — コマンドを書いた発言に紐づけて保存する。別の発言にはしない。**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 出目を `role = 'system'`・`participant_id` 無しの発言として挿入する | 不採用 | 既存の規則の導出を変える。`facilitator_alternating` は末尾が参加者以外の発言なら進行役を選ぶ（§4.5 手順 2）ので、GM が判定を求めるたびに GM が続けて話す。`weighted` は末尾が参加者以外なら連続発言の抑制を誰にも課さない（§4.6.7）ので、振った本人がすぐまた話せる。規則ごとに例外を足すことになる |
| コマンドを書いた発言の列に判定の記録を保存する | 採用 | 発言は 1 件のままなので、4 規則のどれも振る舞いが変わらない。§4.6.5 の呼びかけ先と同じく、保存時に確定し本文から導き直さない |

- 列は `messages.dice_rolls`（JSON 配列、`'[]'` = 無し。migration で追加）。要素はコマンド本文・式・各ダイスの目・修正値・合計・目標値・成否。
  `addressed_participant_ids`（§3）と同じく、発言と一緒に丸ごと読まれるだけなので結合テーブルにしない。
- コマンドの行は本文から剥がし、記録のほうに残す（本文に制御用の記法を残さない、§4.6.5 と同じ扱い）。
- prompt への写像（§4.3）では、本文の後に「【ダイス】行動 — 1d20+3 → 4+3 = 7（目標 12、失敗）」の 1 行を足す。
  自分の発言（`assistant`）にも他人の発言（`user`）にも同じ行を足す。コマンドだけの発言は本文が空で、この行だけになる。
- **1 発言で実行するコマンドは最終行の 1 つだけ**にする。§4.6.5 の指示子 `[次: …]` とは、指示子を先に剥がし、
  残った本文の最終行でコマンドを探す順序で並べる。
- 空の発言の扱い（§4.3、`ErrUtteranceOnlyDirective`）は「本文が空で、判定の記録も無い」ときだけに狭める。コマンドだけの発言は保存する。
- 書式が解釈できない `/roll` 行は、参加者の発言では本文として残し、記録は作らない（ターンを失敗にすると自動進行が止まる）。
  人間の介入発言では 400 で返し、入力欄に残して直せるようにする。

**3. 画面 — 専用ボタンは置かない。入力欄の補完と、発言の下のチップだけにする。**

- 介入欄で `/` を打つと、コマンドの書式の候補（`/roll 1d20+0 目標12 行動` など）を出す。
- 判定の記録は発言本文の下にチップで出す（例: 「🎲 岩棚を渡る 1d20+3 → 4+3 = 7 / 目標 12 失敗」）。モデルが書いた本文とは見た目で区別し、アプリが出した値だと分かるようにする。
- 生成中のストリームには剥がす前の本文が流れるので、コマンド行は生成中だけ見え、`done` で保存済みの本文とチップに置き換わる（§4.6.5 の指示子と同じ）。
- 役割リマインド（§4.3）にはコマンドの指示を足さない。いつ振るか・修正値はいくつかはゲームごとの規則なので、場面設定・役割プロンプトに書く
  （測定もこの形で行った）。同梱 `trpg-table` の「ダイスは使いません」の行は、この規則に差し替える。
  検出は多人数会話のすべての発言で行う。行頭が `/roll` の行を会話で書くことはまず無いので、ダイスを使うかの chat 設定は持たない。

**4. アプリが持つ判定の範囲 — 式を振り、目標値と比べて成否を付けるまで。スクリプト言語は持たない。**

- 書式は `/roll <式> [目標<整数>] [行動]`。式は `NdM`・`NdM+K`・`NdM-K`（N は 1〜20、M は 2〜100）。
  引数の並びは固定で、変数・条件分岐・マクロ・複数の式の組み合わせは持たない。SillyTavern の STscript のような言語は入れない。
- 目標値は、コマンドの `目標N` → 既定の目標値（`chats.dice_target`、0 = 無し）の順で決める。どちらも無ければ合計だけを記録し、成否は付けない。
  既定の目標値を置くのは、コマンドを書くプレイヤー側は目標値を知らない（GM が持つ）のが普通で、読み取り 3 のとおり成否の付かない合計は GM に曲げられやすいからである。
  プリセットは既定の目標値を持てる（同梱 `trpg-table` は 12）。
- 成功は「合計 ≥ 目標値」。クリティカル・ファンブル・有利 / 不利・対抗判定は持たない。必要になれば `/roll` の書式に固定の引数を足す形で別に設計する。

#### 4.8.4 状態項目への効果と前提条件

**効果を生むのは効果コマンドだけにする。`/roll` の成否から効果を自動で導かない。**
成否ごとに効果を分けるには「成功なら A、失敗なら B」の条件を書ける必要があり、それは上で退けたスクリプト言語になる。
判定の結果を見た GM（モデル）か人間が、次の発言で効果コマンドを書く。

| コマンド | 効果（§4.7.3 の基本操作） | 前提条件 |
| --- | --- | --- |
| `/add <持ち主> <項目名> <±整数 または 式>` | `add`。式なら振った合計を加減する（`/add レン HP -1d6`） | 値の先頭が整数であること |
| `/use <持ち主> <項目名>` | `add` で −1（`/use レン たいまつ`） | 値の先頭の整数が 1 以上であること（持っていない物は使えない） |
| `/set <持ち主> <項目名> <値>` | `set` | 無し |

- 持ち主は参加者の名前（§4.6.5 と同じく、表示名そのものか括弧書きを除いた部分）か「共通」。
- **前提条件はアプリが、効果を当てる時点で状態シートの値を読んで判定する。** §4.7.2 の読み取り 3 のとおり prompt では担保できないので、
  判定の場所はここしかない。満たさない効果は適用せず、その旨を判定の記録（チップ）に残す。§4.7.3 の上限超過も同じ扱い。
- 効果の記録は判定の記録と同じ列に並べ、どの発言による効果かを観戦ビューで追えるようにする（TASK-36 の AC #2）。

**TASK-36 は保留にする。** 効果コマンドをモデルが書くかは測っていない。§4.7.2 の更新ブロックと同じく状態の変化を追う必要がある書式なので、
書かれる率は `/roll` より低いと予想される。`/roll` を実装した後、GM が判定の結果を受けて `/add`・`/use` を書くかを測ってから着手する。
書かれなくても人間が同じコマンドを書けるので、効果コマンドの設計自体はそのまま成り立つ。

  チップ表示と入力欄の補完・markdown エクスポート・プリセットの `diceTarget` と同梱 `trpg-table` の規則の差し替え。

## 5. HTTP API

| ルート | 内容 |
| --- | --- |
| `POST /api/projects/{projectId}/chats` | 既存を拡張: `kind: "multi_agent"` を受け付ける。任意で `presetId`（同梱プリセットの id）または `preset`（プリセットの JSON オブジェクトそのもの）を 1 つだけ受け付け、そのプリセットを適用する。両方指定・`kind` が `assistant` のときの指定は 400、未知の `presetId` は 404 |
| `GET /api/multi-agent-presets` | 同梱プリセットの一覧（`id` / `title` / `description` / `group` / `turnRule` / `scenePrompt` / `participants[]`） |
| `POST /api/chats/{chatId}/preset` | 既存の多人数会話にプリセットを適用する。body は作成時と同じ `presetId` または `preset` を 1 つだけ。単独 assistant の chat は 400、未知の `presetId` は 404、`messages` が 1 件以上ある chat は 409。応答は適用後の `{ chat, participants }` |
| `PATCH /api/chats/{chatId}` | 既存を拡張: `turnRule` / `scenePrompt` / `facilitatorId` の更新を受け付ける。`turnRule` は `round_robin` / `manual` / `facilitator_alternating` / `weighted` のいずれか。`facilitatorId` は空文字（指定の解除）か、その chat の編成に居る参加者の id。それ以外は 400 |
| `GET /api/chats/{chatId}/participants` | 参加者一覧 |
| `POST /api/chats/{chatId}/participants` | 参加者追加。任意で `receivesProjectMaterial`（省略時は `true` = 渡す） |
| `PATCH /api/participants/{participantId}` | 参加者更新（表示名・役割プロンプト・接続先・モデル・順序・`receivesProjectMaterial`） |
| `DELETE /api/participants/{participantId}` | 参加者の除籍（論理削除。過去の発言の帰属は残る、§3） |
| `POST /api/chats/{chatId}/turns/stream` | 1 ターン実行（SSE）。body: `{ "participantId"?: string }`（`manual` 時必須）。ターン前の拒否はステータスで返る: 実行中のターンと重なれば 409、chat・指名した参加者が無ければ 404、規則と指名の不整合・除籍済みの指名・空の編成は 400、接続先不通は 502。通れば `speaker`（§4.6.6）→ `delta`… → `done` を流し、それより後の失敗（生成・保存）はストリーム内の `error` になる |
| `GET /api/messages/{messageId}/memory-draft` | 発言のメモリ保存の下書き `{ draft: { content, kind } }`（§4.4）。発言が無ければ 404、単独 assistant の chat は 400、一時チャットは 409 |
| `POST /api/messages/{messageId}/memory` | 発言のメモリ保存。body: `{ content, kind?, locked? }`（`kind` 省略時は推定、`locked` 既定 `true`）。拒否は下書きと同じ。応答は `{ memory }`（`source = multi_agent`、`sharedWithAll` は真） |
| `PATCH /api/documents/{documentId}/shared` | ドキュメントを共通プロジェクト資料に入れる / 外す（§4.4）。body: `{ sharedWithAll: boolean }`。真偽値でなければ 400、未知の id は 404 |
| `PATCH /api/memories/{memoryId}/shared` | メモリを共通プロジェクト資料に入れる / 外す。body・拒否はドキュメントと同じ |

参加者の更新・削除を chat 配下に入れ子にせずフラットな ID にしているのは既存ルートの形に合わせたもので、
同一 chat 検証の要否もそこから決まる（§3 末尾）。
接続先ごとのモデル列挙は既存 `POST /api/configuration/models` を流用する。

**プリセットの適用**とは、chat の `turnRule` / `scenePrompt` をプリセットのものにし、`participants[]` を登録順（= round_robin の巡回順）に
参加者として作り、`facilitator: true` を付けた参加者があればその id を chat の進行役に設定することを指す。
プリセットが進行役を持たないときは進行役を空にする（既存 chat への適用では、置き換える前の編成の id が残らないようにするため）。
プリセット側が participant id ではなく名簿の要素に印を付けるのは、id が適用の瞬間まで存在しないためである。
`turnRule` が `facilitator_alternating` のプリセットは `facilitator: true` をちょうど 1 件持つことを検証する（持たない・複数は 400）。
`weighted` のプリセットは 0 件か 1 件（進行役は任意、複数は 400）。
他のルールのプリセットに印を付けるのも 400 とする（保存されても誰も読まない値になるため）。chat の title が空ならプリセットの `title` を使う。参加者の接続先・モデルは空で作られ、
ターン実行時はワークスペース既定のエンドポイントに落ちる（参加者ごとに変えるのは編成パネル）。
適用後の chat はプリセットとの結びつきを持たない（以後の編集はすべて編成パネル）。新規作成時に参加者の作成が途中で失敗したら chat ごと削除して返す
（repository 層にトランザクションが無く、編成が欠けた多人数会話を残さないため）。

既存 chat への適用（`POST /api/chats/{chatId}/preset`）は**発言が 1 件も無いあいだだけ**受け付ける。
サイドバーの「＋」は空の名簿で多人数会話を作るので、プリセットは作成後に選べる必要がある一方、
発言のある会話で名簿と場面を丸ごと差し替えると、transcript が既に居ない話者を指す。
リクエスト自体は正しく、chat の状態だけが受け付けを拒む状況なので、409 を返す（ターンの重なりと同じ扱い）。
既存の参加者は**追記ではなく置換**し、しかも論理削除ではなく行ごと消す。
**Why**: (1) 適用後の chat は「そのプリセットで作った chat」と同じでなければならず、追記では編成が一致しない。
(2) 論理削除で行を残すと、除籍済み参加者として画面に出続け、`CreateParticipant` の `sort_order` も残った行の次から始まるため、
作成時（0 起点・除籍行なし）と一致しない。(3) そもそも論理削除の理由（§3: 過去発言の話者解決と `round_robin` の巡回起点）は
発言が 0 件なら成立しないので、消して壊れるものが無い。
既存 chat への適用が途中で失敗したときは chat を消さない（利用者が作った既存の chat であり、作成時と違って捨ててよいものではない）。
発言は 0 件のままなので、同じルートでもう一度適用すれば中途半端な編成は消えてやり直せる。

## 6. フロントエンド

- **編成パネル**: 参加者の CRUD、接続先 base URL 入力 + モデル選択（configuration/models 流用）+ 接続確認表示、ターン進行ルールと場面設定の編集。
  ターン進行ルールの選択肢は「規則名 — 1 行の説明」の形で並べる（`weighted` は「呼ばれた人、長く黙っていた人が次に話す」）。
  ターン進行ルールで `facilitator_alternating` か `weighted` を選んだときだけ、その下に**進行役**の選択（編成の参加者から 1 人、または「未選択」）と
  1 行の説明を出す。`weighted` の説明は、進行役が直近発言の抑制を受けないことと、未選択なら全員を同じに扱うことを述べる
  （`weighted` では進行役が居なくても縮退ではないので、「編成にいない」旨の差し替えは出さない）。選択の値は chat が持つ id をそのまま映さず編成と突き合わせ、除籍済みの id は「未選択」として表示する。
  **Why**: 選択肢に無い id を選択状態として見せると、ターンが実際に行うこと（`round_robin` への縮退、§4.5）と画面が食い違う。
  進行役が編成に居ないあいだは、説明文をその旨に差し替え、観戦ビューの進行コントロールにも同じことを 1 行出す
  （編成パネルは折り畳めるので、進行が変わっていることに気付ける場所は観戦ビュー側にも要る）。
  参加者ごとの「プロジェクト資料を渡す」は役割プロンプトの下にチェックボックス 1 つで置き、他の項目と同じ保存ボタンでまとめて保存する
  （どちらもその話者に何を与えるかの設定で、接続先・モデルはどこで実行するかの設定なので、前者の側に置く）。
  既定が ON であることと、OFF ではドキュメント・メモリの検索ごと行わないことは、接続先・モデルと同じ `(?)` のツールチップに載せる。
  接続先・モデルを空欄にするとワークスペース設定を継承することは、各ラベル横の `(?)` のツールチップで示す。ホバーとフォーカスの
  両方で開き（ポインタ無しでも到達できる）、同じ文を `aria-label` にも持たせる。**Why**: プレースホルダーには置けない — パネル幅で
  文が切れるうえ、入力済みの参加者を見直すときには消えている。入力欄の下の常設の補足行も採らない — モデル側だけで 4 行を占有し、
  一度読めば以後は流すだけの説明に恒久的な場所を使うことになる（実機で確認）。吹き出しは**上向き**に開き、幅はテキストなりではなく
  行幅に固定する。下向きだと説明している当の入力欄を覆って入力内容が見えなくなり、テキスト幅だと長い訳文が `overflow: auto` の
  パネルからはみ出して切れる（いずれも実機で確認）。
- **「全参加者に渡す」の操作**（TASK-31）: プロジェクト詳細のドキュメント一覧とメモリ一覧に、1 クリックで切り替わる
  アイコンボタンと、真のときだけ出るバッジを置く。ドキュメント詳細モーダルにはチェックボックスと 1 行の説明も置く。
  下書き + 保存ボタンにしないのは、切り替える値が真偽値 1 つで、カテゴリのように候補から選ぶものではないため。
- **観戦ビュー**: ChatPage のストリーミング表示を踏襲し、発言者の表示名・モデル名を発言に付す。進行コントロールは「1 ターン進める」「自動進行の開始 / 停止」（= フロントのループ、§4.1）「（manual 時）次の発言者の指名」。
  生成中の話者名・モデル名はターンの SSE の `speaker` イベントだけで決まる（§4.6.6）。フロントは規則を複製せず、
  `speaker` が届くまでは「ターン実行中」とだけ出す。`manual` の指名候補は編成から直接並べる。
- **markdown エクスポート**: 観戦ビューのヘッダから `GET /api/chats/{chatId}/export/markdown` を呼び、見出し（chat タイトル・
  プロジェクト名・出力日時）、場面設定、ターン進行ルール、編成、話者名つきの発言を 1 枚の markdown として保存する。
  生成は `internal/service/export.go`。ルートは chat 単位で単独アシスタントの chat にも効き、その場合は場面設定・
  ターン進行ルール・編成の 3 節が落ちる。話者名は `ListAll` の全行で解決するので除籍済みの参加者の発言も帰属が残る（§3）。
  保存は Wails の `SaveTextFile` 束縛（ネイティブの保存ダイアログ）。WebView の外（`window.go` が無い環境）では
  Blob ダウンロードに落ちる。Wails v2.16 の macOS 実装はダウンロードのデリゲートを実装していないため、
  `<a download>` だけでは WebView 内で無言で失敗する。
- **プリセット**: 新規作成フォームで `kind = multi_agent` を選ぶとプリセット選択が出る。同じ選択 UI（`components/PresetPicker.tsx`）を
  編成パネルの先頭にも置き、**発言が 1 件も無いあいだだけ**「このプリセットを適用」を出す（発言が 1 件でもあれば選択 UI ごと出さない）。
  パネル側は `<details>` で既定は折り畳み、開閉状態は保存しない。作成時にプリセットを選んだ chat では編成が既に埋まっており、
  済んだ判断のための節が編成の上に開いたままになるため。編成に参加者が居るときは置き換える旨を in-app の確認ダイアログで確かめてから適用する。同梱プリセットは群（`discussion` 議論・検討 /
  `drama` 演技・雑談 / `hosted` 聞き手つきの対話 / `pair` 1 対 1）ごとに `optgroup` で並び、「プリセットの JSON を読み込む」で
  ローカルの JSON ファイルを選ぶと、その内容を `preset` としてインラインで送って適用できる（読み込んだファイルは一覧には残らない）。
  保存形式は同梱分が `internal/preset/bundled/*.json`（`go:embed`）、追加分が `presets/multi-agent/*.json`（形式の説明は同ディレクトリの README）。決めた理由は §8「実装で解消した判断」。
  プリセットの `participants[]` は任意で `receivesProjectMaterial` を持てる（省略時は `true`）。GM だけがシナリオを読む編成は
  プリセットの側で表現できるべきで、適用のたびに編成パネルで設定し直すものではない。同じ理由で `facilitator`（真偽値、省略時は偽）も持てる。
  同梱の `trpg-table`（GM + プレイヤー 2 名）が両方を使い、`facilitator_alternating` で GM だけがプロジェクト資料を読む卓になる。

## 8. 実装で解消した判断と、将来拡張で判断する事項

「実装で解消した判断」とは、起票時に未決として挙げ、実装の中で決着して本文（§3〜§6）へ反映した項目の記録を指す。
「将来拡張で判断する事項」とは、現行実装の完成を妨げず、§7「将来」の拡張に着手するときに判断すればよい論点を指す。
起票時の未決はすべてどちらかに振り分けてあり、現行実装の側に残っている未決は無い。

### 8.1 実装で解消した判断

- **履歴圧縮への summary サービス流用 → 見送り**（2026-09-19）: 直近 30 発言の切り詰めのみとし、要約は入れない。
  **Why**: (1) 毎ターン要約の LLM 呼び出しを足すとローカル小型モデルでは 1 ターンの遅延が倍になる。
  (2) `chat_summaries` は単独 assistant フローの要約で、流用すると §4.4 の分離が崩れる。
  (3) 検討記録 §2 と実機で見えた崩れ方は「事実の忘却」より「役割の忘却・同調」で、これは毎ターンの役割リマインド（§4.3）が受け持つ。
  進行役を置くプリセットでは 1 巡ごとに進行役が要約するので、履歴が切れても文脈が残る（プリセット側の対策）。
  要約が必要になったら多人数会話専用の要約列を chat に持たせる形で足す（`chat_summaries` は流用しない）。
- **プリセットの保存形式 → 同梱 JSON + JSON ファイルからのインライン適用**（2026-09-19）:
  同梱分は `internal/preset/bundled/*.json` を `go:embed`、ファイルからの適用は §5 の `preset`。
  **Why**: エンジン（コード）とプリセット（データ）を分ける §0 の方針に沿い、Go を触らずにプリセットを足せる。単一バイナリも保つ。
  データディレクトリの走査による永続的な追加は、読み込み失敗時の扱いと UI が増えるので入れない。必要になれば `presets/multi-agent/` の
  形式のまま `<dataDir>/multi-agent-presets/` を一覧に足す拡張で対応できる。
- **既存 chat へのプリセット適用の可否と既存参加者の扱い → 発言 0 件に限って許可し、編成は置換**（2026-09-20）:
  ルートは `POST /api/chats/{chatId}/preset`、既存の参加者は行ごと削除してから作り直す。理由は §5 の該当段落。
  適用はターンエンジンの chat 単位の排他（§4.2 手順 0、`TurnEngine.WithTurnExcluded`）と、
  人間の発言保存と共有する chat 単位の書き込みロック（`TurnEngine.WithMessageWrite`）の両方の中で行い、
  発言の有無もその中で読む。**Why**: ターンは発言者を選んでから完了時に message を保存するので、
  排他の外で編成を消すと、保存された message が既に消えた参加者を指し、話者を解決できない発言が残る。
  人間の介入発言は編成を必要としないので、発言の有無を読んだ直後に入り込み、発言済みの会話に
  プリセットが当たった状態を作る。ターンが走っているあいだの適用は 409、人間の発言は待たせる
  （ターンの最中に介入できること自体は §4.4 の仕様なので、ターンの排他には入れない）。
  **Why**: サイドバーの「＋」で空の名簿の多人数会話を作れるようになった（TASK-13）ため、作成フォーム以外にプリセットを選ぶ場所が要る。
  発言のある会話まで許すと transcript が既に居ない話者を指すので、そこは 409 で拒む。
- **多人数会話へのプロジェクト資料の取り込み → `PromptContext` の流用ではなく専用の組み立て関数**（2026-09-21、TASK-18）:
  起票時の §4.4 は retrieval / memory を一切使わない分離だったが、方針を変えてドキュメントとメモリをプロジェクト資料として渡す（現行の §4.4）。
  単独 assistant の `ContextService.Assemble` が返す `PromptContext` を流用する案は却下した。
  **Why**: `PromptContext` は背景知識だけでなく振る舞いの指示を含む。引用モード判定（`reQuoteRequest`）は
  「そのまま」「引用」「原文」を含むだけで発火し、会話のセリフで誤発火して次の話者に「提供文書からのみ引用せよ」が入る。
  手続きメモリは無条件で全文注入される。プロジェクトのシステムプロンプトはアシスタント向けの指示で、役割を演じる話者には向かない。
  system prompt は 1 本の文字列なので、後段の場面設定・役割がこれらを上書きする保証は無い。
  `Assemble` 本体には手を入れず（単独 chat の挙動を変えないため）、多人数会話用の小さな関数を足した。
- **AGENTS.md「Core product shape」への追記文面 → 反映済み**（2026-09-19）: chat を「単独 assistant」と「多人数会話」の
  2 種別として書き、参加者・ターン進行ルール・場面設定・プリセットを多人数会話の構成要素として並べた。
  **Why**: 多人数会話は projects / documents / chats / memories と並ぶ第 5 の製品要素ではなく、chat の種別である（§2）。
  並列の箇条書きに足すと、project 配下に別系統のデータがあるように読める。
  同じ区分（chat の種別として書く）を [AGENTS.ja.md](../AGENTS.ja.md)・[README](../README.md)（[ja](../README.ja.md)）・
  [current-spec](./current-spec.md)（[ja](./current-spec.ja.md)）にも通した。

- **進行役を挟むターン規則の、進行役不在時と人間の介入発言後の扱い → `round_robin` への縮退と、進行役が応じる**
  （2026-09-22、TASK-21、ユーザー判断）: 起票時に着手時判断として残っていた 2 点。決めた内容と理由は §4.5 にある。
  導出は `selectSpeaker`（[turnengine.go](../internal/service/turnengine.go)）だけにあり、フロントは話者を
  `speaker` イベントで受け取る（当初はフロントの `turnOrder.ts` にも同じ導出を複製していたが、TASK-33 で削除した）。
  画面は進行役が編成に居ないことを編成パネルと観戦ビューの双方に出す（§6）。

### 8.2 将来拡張で判断する事項

いずれも現行実装では不要で、§7「将来」の該当拡張に着手するときに判断する。

- 参加者ごとの API キー列の要否（LM Studio では不要。他の OpenAI 互換サービスを見据えるなら追加）。
- 多人数会話への review サービス適用の要否。
- 人間が参加者の一枠として発言するモード（TRPG のプレイヤー参加）の UI 設計。

**発言本文の呼びかけから次の話者を導く規則は TASK-34 で実装した**。以下は TASK-28 の spike の結論の要約である
（2026-09-22、TASK-28、spike、ユーザー判断）。スコア方式（`weighted`、係数の積で話者の重みを求める）と、
呼びかけ先を最優先する順位規則（`addressed_first`）をシミュレーションで比較し、`weighted` を採った。
係数・同点規則・検出方式・保存形式・画面への出し方・人間の介入発言の後の話者をすべて §4.6 で決めてある。
呼びかけは末尾のメッセージだけでなく**直近 n 参加者発言の窓**のうち未応答のあいだ効く加点として表す
（2026-09-22 のユーザー提案。起票時の「呼びかけ先以外を ×0.5」から替えた）。
窓を与えた順位規則とは測定上互角で傾向が違い、採った理由は呼びかけを他の圧力と競合させられることにある
（§4.6.3 読み取り 6、§4.6.4）。SillyTavern の `talkativeness` を入れない判断は §4.6.10。
実装は §4.6.1・§4.6.4〜4.6.7 をそのまま実装し、細部は §4.6.5 の「実装で決めた細部」に記録した。
